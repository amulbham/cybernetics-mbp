## Why a direct upload and not the normal staging workflow
The workflow `.github/workflows/deploy-pages.yml` runs `npm run build:pdfs` for every ref, which typesets every PDF fresh with Vivliostyle (not byte-reproducible), and its carry-over and six-PDF guard steps run only for `main`; the workflow also builds from Git, and the candidate source is private and on no branch. Evidence from the live target: the staging alias today serves five historical PDFs that **differ** from the approved bytes (only Cognition equals it; `T29.4-staging-pre-upload-state.tsv`). The workflow therefore cannot preserve the approved PDF bytes or the candidate PDF; the owner-run direct upload of the verified folder is the chosen path.

## Owner steps (nothing has been run)
1. **Package.** The Executor sends `paper-c-staging-upload.zip` with its SHA-256 (a zip is not byte-deterministic; only the directory digest is pinned). Extract to a new empty folder near a drive root (Windows path length).
2. **Verify the folder.** `node verify-upload-dir.mjs <folder>` must print `PASS`; compare the printed directory digest with `0cf5cc89…ff834` and the kit digest with the GO by eye. If the Executor cannot supply the zip, `node assemble-staging-tree.mjs --html <candidate/html> --candidate-pdf <pdf> --legacy <six PDFs> --pagefind <node_modules/.bin/pagefind> --out <new folder>` rebuilds the identical tree from the review set.
3. **Upload once.** From an empty folder outside any repository (no `functions/` or `wrangler.toml`), sign in with `npx wrangler@4.129.0 login` (or `$env:CLOUDFLARE_API_TOKEN = Read-Host 'token'`), then run exactly:
   `npx wrangler@4.129.0 pages deploy <FOLDER> --project-name cybernetics-mbp-site --branch staging --commit-hash 63372f2b73d4d5287e92d283a4e71ee766a95e75 --commit-message "T29.4 Paper C candidate staging preview"`
   `--branch staging` is mandatory and explicit; never `main`. Record the printed counts, the **deployment-specific URL** (`https://<8 hex>.cybernetics-mbp-site.pages.dev`) and the alias URL, and send them to the Executor. Stop if Wrangler mentions Functions or `_worker.js`.
4. **Verify (Executor, public, no credentials).** `node verify-staging.mjs --origin <deployment URL> --production --out staging-verification-report.json`; then `NODE_PATH=$(npm root -g) node capture-staging.mjs --origin <deployment URL> --report staging-verification-report.json --out captures`. The first checks the 187 inventory files minus the two control files on the deployment URL **and** the alias (seven PDFs byte-exact, article byte-exact, other non-HTML byte-exact, exact `X-Robots-Tag`, all 25 redirect rules, closed indexing) and that `amulbham.com` is untouched; the second captures desktop 1440×900 and mobile 390×844 images of the full article at the deployment URL and runs the article, download and search checks. Dry run on the real tree through the local Pages-like server: 187 files, seven PDFs matched, 25/25 redirects, 84 desktop and 145 mobile images, all 21 assertions PASS.
5. **Review.** The owner reviews desktop and mobile (the captures and a browser of their own) and records acceptance or changes bound to the deployment URL and the candidate PDF hash.

## Rollback
No Git ref, workflow, variable or production setting changes, so rollback is a staging-alias restore only.
1. **Restore the previous staging content** (the Pages dashboard offers rollback for production deployments only): GitHub → Actions → "Deploy Pages (HTML + scholarly PDFs)" → Run workflow → branch `staging`. It redeploys `staging` @ `3f2b0369…` to the same alias (`--branch staging`). The PDFs it serves are re-typeset, as before the upload.
2. **Verify** with `node verify-staging.mjs --rollback-check`: the alias must serve every recorded page (the 16 HTML pages in `T29.4-staging-pre-upload-state.tsv`) with its recorded hash; PDF differences are informational. The rebuild is **expected, not proven**, to reproduce those hashes (hashed asset names can differ between builds). On a mismatch, stop and report which pages differ; do not re-run the workflow repeatedly or edit anything, and the owner decides. Deployment `2d879b27` remains reachable at its own URL as the reference. All six PDFs are re-typeset by the rollback, including Cognition, which equals the approved bytes today. The Paper C deployment URL stays public until deleted (step 3).
3. **Optional removal** of the Paper C deployment URL: `npx wrangler@4.129.0 pages deployment delete <DEPLOYMENT_ID> --project-name cybernetics-mbp-site --force`, only after step 1 (the latest deployment of a branch cannot be deleted). Never delete `2d879b27`. Removal cannot recall copies already taken.
If the upload itself fails before completing, nothing is replaced and no rollback is needed; re-verify the alias against the pre-upload state.

## Limits of the dry run
The local dry run serves the tree through a Pages-like mock where the alias equals the origin, so the alias branch of the host check is exercised by unit tests, not end to end; the real check against Cloudflare happens after the upload. The capture index is an attestation of what the Executor's browser saw and can be forged by whoever runs it; the owner's own review is the acceptance control.

## Evidence classes
Executor-reproducible: the tree, digest, `verify-staging` results, captures. Owner-supplied: the Wrangler output and the visual decision.
