## Questions this ticket may answer

1. **Identity** — what makes an IWL identifiable as belonging to exactly one Article? What would a collision or an orphaned IWL look like, and how should the architecture make that structurally hard?
2. **Route architecture** — should an IWL live at a subordinate path under its parent Article's canonical URL, or as a sibling top-level route with an explicit parent reference? What does `research-routing.ts`'s existing model make cheap vs. expensive?
3. **Source ownership** — should IWL source be co-located with its parent Article's source (matching the `research` collection's existing per-piece directory convention), or live in a separate collection? What does the discovery/build pipeline already assume that would make one option safer?
4. **Presence vs. publication authorization** — what is the minimal, author-edited signal (frontmatter field, file presence, explicit flag) that expresses each of the three states without inferring anything at runtime?
5. **Minimal envelope** — what is the smallest set of fields/metadata the outer contract actually needs (title, parent reference, publication state) versus what would be premature?
6. **Rendering boundary** — can the IWL's authored body render through the existing Markdown/MDX pipeline and a plain shell without requiring any parsing of its internal structure? Where exactly would internal structure leak into the render path if not deliberately kept opaque?
7. **Human navigation** — where, if anywhere, does a link from Article → IWL and IWL → Article belong, matching the "no empty navigation" constraint? What does Sprint 12's `readerNote` eligibility precedent suggest about earned vs. inferred UI?
8. **Internal search/discovery** — should Pagefind index IWL content by default, and does the current Pagefind configuration make exclusion or inclusion the lower-risk default?
9. **Privacy boundary** — what evidence in Fixture C (the real IWL) demonstrates that some content is publication-sensitive, and what does that imply about the boundary between "exists in source" and "authorized for public display"?
10. **PDF behavior** — does the existing PDF build/validate pipeline need to be aware of IWL routes at all in Sprint 13, or can it safely remain scoped to Articles only?
11. **Public semantics** — is any Article↔IWL JSON-LD relation earned yet, or does Sprint 12's `backstory` precedent (semantic silence over an approximate claim) apply here too?
12. **Real-fixture pressure test** — walking Fixture B and Fixture C through each candidate outer architecture: does the architecture hold without contradiction, without requiring any inner-grammar decision, and without exposing anything Fixture C's content suggests should stay unpublished?

## Required outputs

### A — Evidence matrix

1. **Identity** — `research-routing.ts`'s `canonicalPath()`/`categorySegment()` derive routing entirely from an entry's own `format`/`pillar`/`id`; no parent-reference concept exists today. Fixture C's own "Document Identity" block carries a `Published alongside: [link to paper on publication]` field — real evidence the author already manually tracks a parent-Article reference *inside* the IWL source itself. → the outer contract should make the IWL the side that references its parent, not the reverse.
2. **Route architecture** — no existing route nests one research entry under another. `canonicalPath()` is the single routing authority every consumer (the `[category]/[slug]` route, `ResearchLayout`'s `canonicalURL`, `discover-research.mjs`, the OG-image route) already shares. Extending it (not duplicating it) to emit a nested child path is the lower-risk direction; a sibling top-level route with a hand-carried parent field is the higher-risk one (real precedent: a hand-duplicated `canonicalURL` field once drifted, per this file's own header comment).
3. **Source ownership** — the `research` collection's `glob` loader already scans `{slug}/index.{md,mdx}` folders; no folder today holds more than one content file. Fixture C is substantial authored prose (39KB extracted text, comparable in scale to Fixture B's 52KB) — a real document, not a metadata sidecar. `content.config.ts`'s own header comment records that this project actively regrets its one prior collection fragmentation (`papers`/`blog`, unified 2026-08-20) — real precedent favoring a sibling file in the same collection or a small, explicitly-referencing satellite collection over an unrelated parallel system.
4. **Presence vs. publication** — every optional field in the current schema (`readerNote`, `doi`, `heroImage`) is binary present/absent; none expresses a third state. Fixture C's own bracketed `[link to paper on publication]` placeholder is direct evidence the author already distinguishes "drafted" from "linked/published" by hand. A dedicated `publicationState`-shaped field (not file presence, not git branch) is required to keep the three states genuinely separate.
5. **Minimal envelope** — `consts.ts`'s `AUTHOR`/`LICENSE` constants already separate "varies per piece" from "always the same," and Fixture C's own Document Identity block (Title/Artifact version/IWL version vary; Author/ORCID/License repeat the same constant this site already has) mirrors that split exactly. Envelope = title (or derived), parent reference, publication state, dates — author/license/affiliation reuse the existing constants, never re-authored per IWL.
6. **Rendering boundary** — both fixtures are ordinary long-form Markdown-shaped prose (headings, tables, parenthetical `(Author, Year)`-style citations already in the exact idiom `rehype-citation-links.mjs`/`rehype-references.mjs` parse today). The four named surfaces are just headings and tables in that render — the existing pipeline can render Fixture C's body with zero new parser, which is what the governing opaque-body rule requires structurally, not just by policy.
7. **Human navigation** — two real, shipped "genuine absence" precedents already exist: `RelatedResearch.astro` (renders nothing when there's no real relation — documented in `ROADMAP.md`) and `readerNote`'s `&&`-gated `reader-context` slot (Sprint 12.1). Either precedent extends directly to a conditional Article↔IWL link with no new absence pattern needed.
8. **Internal search/discovery** — confirmed directly, twice: a repo-wide search found no `data-pagefind-ignore`/`data-pagefind-body` usage anywhere, and `npm run build`'s own Pagefind output states plainly: *"Did not find a data-pagefind-body element on the site. ↳ Indexing all `<body>` elements on the site."* Pagefind indexes every built page unconditionally today. H5 (exclude-by-default) is **not** already true — it would require adding a new opt-out mechanism that does not exist in this codebase yet.
9. **Privacy boundary** — Fixture C is itself already a curated, publication-candidate document (it has its own version identity, an explicit "Published alongside" field expecting a real URL, and its own Version History records that an earlier, superseded "IWL v1" internal draft already existed and was replaced by v2). Its Methodology Note *describes* the AI-collaboration process in the author's own retrospective prose; it never embeds a raw chat transcript or hidden model reasoning. "Source exists" in the three-state model should mean "a curated document like Fixture C exists," never "raw development artifacts exist" — raw chats stay a separate, Sprint-14-scoped, presumed-private category untouched by this ticket.
10. **PDF behavior** — `build-research-pdfs.mjs` calls `discoverPapers()` exclusively, which filters to `format === 'paper'` only. An IWL entry that never declares `format: 'paper'` is already, structurally, excluded from PDF generation with zero code change — confirmed by reading the discovery/build scripts directly, not assumed.
11. **Public semantics** — `research-relation-projections.ts`'s `PROJECTION_PROPERTIES` whitelist currently contains exactly one entry (`isBasedOn`), added only via a separately-sealed decision; `readerNote.for → audience` was likewise a standalone, deliberate T12.2 decision. No "default-on" public-semantic path exists anywhere in this codebase. No Article↔IWL JSON-LD property is earned by this ticket.
12. **Real-fixture pressure test** — both fixtures were walked against Candidate 1/2 below without contradiction: the "Published alongside" field maps cleanly onto a parent reference; the four surfaces render as ordinary content; the document's curated-not-raw nature fits the SOURCE-EXISTS state cleanly; nothing in either fixture requires a node/edge schema merely to render correctly.

### C — Candidate outer architectures

1. **Sibling file, nested route** (lowest structural risk) — `src/content/research/{slug}/iwl.md` in the existing `research` collection; route `/research/{category}/{slug}/iwl/`, computed by extending `canonicalPath()`; reuses `ArticleShell`/`ResearchLayout`'s render path with a reduced prop set; `publicationState` field gates `getStaticPaths`; Pagefind opt-out would need to be added explicitly if desired.

More schema surface, but makes "exactly one valid parent" a build-time guarantee rather than a filename convention.
3. **Route-level flag only, no schema field** (rejected) — presence expressed purely by file placement, no `publicationState` field at all. Rejected: collapses SOURCE-EXISTS-UNPUBLISHED into ABSENT or PUBLISHED, violating the sprint's own three-state hard constraint. Recorded only so `T13.1` can see it was considered and why it fails.

Candidates 1 and 2 both survive the real-fixture pressure test against Fixture B/C without contradiction; Candidate 3 fails by construction and should not be carried forward.
