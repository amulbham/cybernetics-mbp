### PDF mechanism (frozen artifact; `carry-over-pdfs.sh` only)
Artifact source: a content-addressed file committed in the release commit at `site/release-pdfs/<sha256>.pdf`, outside `public/` and `dist/` so it is never served. Its bytes are fixed by Git's object hash, the commit SHA the Product Authority approves, and the filename, which must equal the file's own SHA-256.

Release expectation (the binding that the blob alone cannot give; both blobs exist, so presence proves nothing). `site/release-pdfs/expected.txt` is a committed file of `sha256sum` lines — each `<sha256>  research/<category>/<id>/<id>.pdf`, the path identifying the article. At G3 it holds exactly one line: the Chisel path with `H_new`. The script checks it in `guard` mode, which is the first workflow step, before any build or deploy, in every mode including `PDF_RELEASE=new-version`, and again at the start of `carry`. Rules: if the file exists, `PDF_MANIFEST` must be non-empty and must contain every expectation line byte for byte; an expectation path listed with a different hash, an absent path, a malformed line or an empty manifest fails the run with an `::error::` annotation. If the file does not exist, behavior is unchanged. The file is part of the reviewed commit, so a v9 build can only be deployed under a manifest that names `H_new`.

`carry` change (about 40 lines in total with the expectation check; workflow executable lines untouched). For each manifest line, after the existing fetch from production: if the fetched file's SHA-256 equals the manifest hash, nothing changes. If it differs (and the path is not the existing Desk bootstrap), then:
- (a) require `release-pdfs/<manifest-hash>.pdf` to exist, else fail with an `::error::` annotation naming the path and the hash;
- (b) require its SHA-256 to equal its filename and its first five bytes to be `%PDF-`, else fail;
- (c) install it at `dist/<path>`; count the swap; fail if more than one path is swapped in a run;
- (d) the existing all-five `sha256sum -c` against the manifest then runs unchanged; `verify` (post-deploy, live files vs manifest) is unchanged.
A blob never replaces a production file that already matches the manifest. A swap needs three independent things: the owner-set manifest line, the reviewed blob, and the reviewed expectation line agreeing with the manifest. A missing or wrong-hash artifact, or a manifest that contradicts the expectation, fails before deploy and leaves production unchanged. Swap counts: exactly one on the initial transition (production still serves `6d169f28…`); zero on every run where production already serves `H_new` (a re-run, the About release, any later build), when ordinary carry-over fetches the bytes from production and the blobs go unused.

Manifest transition (the owner changes the variable; the Executor never does):
1. Preflight (owner): `PDF_CARRY_OVER=true`, `PDF_RELEASE` unset, `PDF_MANIFEST` = the current five lines.
2. G2: Executor downloads the staging-built Chisel PDF (cache-busted), records `H_new` and size; Product Authority approves those exact bytes. They are frozen: no later rebuild replaces them.
3. G3: the candidate adds `release-pdfs/<H_new>.pdf`, `release-pdfs/6d169f28….pdf` (the retiring production bytes, from a fresh production download, for rollback only) and `release-pdfs/expected.txt`.
4. Release gate (owner): sets `PDF_MANIFEST` to the four unchanged lines plus the Chisel line with `H_new`; the Executor pushes only after the owner says so in chat. If the variable is changed but nothing is pushed, nothing deploys.
5. If the push runs under a stale manifest, the guard fails the run before build and deploy; production is unchanged and nothing is served that the Product Authority did not approve.
6. Recovery authority (see Git and deployment boundary): G4 covers one push of the approved SHA and re-runs of that same SHA only while a run has failed before the deploy step (for example after the owner corrects the variable). Anything else — a run after the deploy step, a rollback, a different SHA — is a recovery action that needs separate Product Authority authorization. Rollback, pre-described so it can be authorized quickly but not granted here: the owner restores the old Chisel manifest line, and a commit sets `expected.txt` to the `6d169f28…` line, reverts the article and IWL, and keeps `release-pdfs/`. Valid only before a Zenodo deposit exists; afterwards forward-fix only.
