## Mechanism (what changes; closed everywhere until the variables are set)

- **One switch**, `src/lib/indexing.mjs`: a build is indexable only when the build env has `SITE_INDEXING=open`. The workflow sets it `open` only if `github.ref_name == 'main'` **and** repository variable `SITE_INDEXING == 'open'`; every staging push, preview or non-`main` run is `closed`; unset is `closed`.
- `BaseHead` derives `noindex, nofollow` from the switch; pages can only add `noindex`. Always-noindex pages (`staysOut()`): `/search/`, `/404`, **every tag page (all 41 stay navigable with unchanged URLs, links and content)**, and any landing page with no entries (`/research/ai-systems/` today, route-only `/research/memos/`; automatically indexable once an entry exists).
- `robots.txt` is generated from the same switch: closed is byte-identical to today's; open is `Allow: /` plus `Sitemap: https://amulbham.com/sitemap-index.xml`.
- Sitemap = every page that does not stay out: **13 URLs** from the present corpus (home, about, research index, three populated category pages, six entries, the Chisel IWL page); verified from the open-mode build (rev 1's 54 included the 41 tag pages).
- `public/_headers` (pattern unchanged from rev 1; Cloudflare documents the syntax, **actual response behavior is UNVERIFIED until S1**): `X-Robots-Tag: noindex, nofollow` on `https://:project.pages.dev/*` and `https://:version.:project.pages.dev/*`; never matches `amulbham.com`.
- `scripts/validate-indexing.mjs` runs in `npm run build` and fails on any disagreement among page meta, `robots.txt`, sitemap and `_headers`.
- **PDF identity (`site/scripts/carry-over-pdfs.sh`, `main` only, opt-in):** while repository variable `PDF_CARRY_OVER == 'true'`, after `build:pdfs` and before `validate:pdfs` and deploy the script (1) requires repository variable `PDF_MANIFEST` — exactly five `sha256sum` lines (the S2/S3-approved production hashes; the Desk line is the Zenodo-verified hash); (2) requires the built PDF set to equal the manifest set exactly (no missing, no unexpected file); (3) replaces each PDF with the one `https://amulbham.com` serves (fixed origin; the rev 1 `PDF_CARRY_OVER_BASE` override is removed); (4) requires every byte to match the manifest. Any defect exits non-zero and nothing deploys. After the upload a final step re-downloads the five live PDFs and re-checks them (`verify`).
- **PDF release guard (final correction; same script, `guard` mode, first step after checkout, `main` only):** persistence rule — once the production manifest exists, an ordinary `main` deployment can never regenerate and replace the approved PDFs. The guard stops the run before anything is built or deployed when `PDF_MANIFEST` is non-empty **and** `PDF_CARRY_OVER` is not `true`, unless `PDF_RELEASE` is exactly `new-version`. It passes when there is no manifest (the initial S2 content release, because the Desk PDF does not exist in production yet) and when carry-over is on (the `carry` step then enforces the manifest). `PDF_RELEASE=new-version` is the only value that authorizes regeneration, and it means one thing: **a new Zenodo version of an already published record** (or a new paper) is being released. Replacing the bytes behind an already published Zenodo version is never authorized by this guard — Zenodo files of a published version are immutable, so a changed PDF requires a new version first. A separately authorized PDF release: (1) Product Authority sets `PDF_RELEASE=new-version` and `PDF_CARRY_OVER` to `false`; (2) the `main` run deploys the new PDFs; (3) the Executor hashes them and the Product Authority uploads them as the new Zenodo version; (4) the Product Authority sets the new `PDF_MANIFEST`, `PDF_CARRY_OVER=true`, and unsets `PDF_RELEASE`; (5) a carry-over redeploy re-verifies the five hashes.

## Rollback

1. **Immediate (minutes):** Cloudflare Pages → Deployments → roll production back to the last known-good deployment (the pre-launch `1f60e21` deployment for a content problem; the S2 closed deployment for an indexing problem), then verify `amulbham.com` directly. Rolling back to the S2 deployment also restores the S2 PDF bytes.
2. **Indexing off without touching content:** set `SITE_INDEXING` to anything other than `open` (or delete it) and re-run the `main` workflow **with `PDF_CARRY_OVER=true` and `PDF_MANIFEST` still set**, so the PDFs stay byte-identical; verify the closed matrix and the five hashes. For already-crawled URLs use `noindex` (never add `Disallow`, which stops crawlers from seeing it) and Search Console Removals for urgent cases.
3. **Carry-over or guard failure:** a guard stop ("manifest exists but carry-over is off") means someone is deploying without the approved PDFs — set `PDF_CARRY_OVER=true` and re-run, or use the PDF release procedure; never unset `PDF_MANIFEST` to get past it. A manifest/hash mismatch fails the run before the upload; nothing is deployed and production is unchanged. Do not "fix" it by unsetting carry-over — investigate, because it means the live PDFs differ from the approved bytes.
4. **Source:** `git revert` the offending commit on `main` (never force-push). A content rollback never needs the indexing variable changed.
- Never merge `staging` into `main`; never combine an indexing change and a content release in one run.
