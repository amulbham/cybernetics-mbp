## Deploy workflow — staging → production

**Deploy authority is GitHub Actions end to end, as of Sprint 9 (9.0–9.5, 2026-09-04) — not Cloudflare's native Git integration.** `.github/workflows/deploy-pages.yml` runs `npm ci` → `npm run build` (Astro + Pagefind) → `npm run build:pdfs` → `npm run validate:pdfs` → the pinned `wrangler pages deploy` (`npm run deploy:pages`, exact version `4.129.0`, Sprint 9.0 — `package-lock.json` fact, never network-resolved) for every push to `staging` or `main`, plus `workflow_dispatch`. Cloudflare's own Git-integrated build is **off** for both branches (Cloudflare dashboard, Build → Branch control — production auto-build off since 9.4, preview auto-build off since 9.3) and no longer ships either — a push's only real build is the Actions one. Cloudflare Pages project: `cybernetics-mbp-site`, production branch `main`, preview branch `staging`, root directory `site`, output directory `dist`, Node 22+.

- **`main`** is production, deployed by Actions on every push.
- **`staging`** is the working branch, also deployed by Actions on every push. Stable branch alias: `https://staging.cybernetics-mbp-site.pages.dev/` (always reflects the latest Actions-deployed `staging` push; per-commit preview URLs like `https://<hash>.cybernetics-mbp-site.pages.dev/` also exist but change on every push).
- **Day-to-day**: do work on `staging`, push, check the preview, iterate as many times as needed — nothing reaches `amulbham.com` until `staging` is merged into `main`. Merge via GitHub PR (`github.com/amulbham/cybernetics-mbp/pull/new/staging`) or a direct `git merge staging` into `main` — either way, verify the live preview *before* merging and re-verify production *after*, since a merge triggering a build isn't the same as confirming the build actually shipped what you expect (and now, additionally, isn't the same as confirming the Actions run itself went green through the deploy step — check the run, not just the resulting URL).
- **A real bug found live during 9.3's own cutover test, not a Cloudflare-side problem**: the deploy step used to splice `${{ github.event.head_commit.message }}` directly into the shell script's `--commit-message="..."` — GitHub substitutes `${{ }}` expressions as raw text *before* bash parses the line, so a commit message containing an embedded `"..."` phrase closed that quoted string early and the rest of the message became bogus extra CLI arguments (confirmed exactly from the failing job's own log). Fixed by passing the value through an intermediate `env: COMMIT_MESSAGE` var and referencing it as `"$COMMIT_MESSAGE"` — bash doesn't re-parse for quote characters inside an already-double-quoted variable expansion. Full writeup: `CHANGELOG.md`. The general lesson: any dynamic/untrusted `${{ }}` value used inside a `run:` block belongs in `env:` first, never spliced into the script text directly.
- **Rollback, two levels — read this before touching either.** *Immediate*: Cloudflare Pages → Deployments → roll production back to the last known-good deployment → verify `amulbham.com` directly (don't assume the rollback UI's own confirmation is enough). *Pipeline*: only if Path B itself (the Actions workflow) is what's actually sick — re-enable Cloudflare's native Git auto-build for production (and preview, if needed) → accept HTML-only PDFs as the temporary state until Actions is fixed → **do not** flip `SITE_WIDE_NOINDEX`/`robots.txt` as a compensating move; indexing state is unrelated to which build system is shipping the HTML.
- **When polling a preview/production URL to confirm a deploy landed, check for a marker that's only true on the *new* build — not just present on both old and new.** A `grep -q "some string"` check that's already true on the previous deploy will report "live" immediately without the new build having actually shipped (hit this for real: checking for `"function initToc"` passed instantly because the *old, buggy* build already contained that string too — just twice instead of once — so the fix's absence went unnoticed until the actual occurrence *count* was checked). Also add a cache-busting query param (`?cb=<random>`) when re-checking after a fix — Cloudflare's edge cache can keep serving stale HTML for a bit past when the new build actually finished.

## Indexing state — READ BEFORE TOUCHING

Indexing is **fail-closed and controlled by one switch** (T22.0): a build is indexable only when the build environment sets `SITE_INDEXING=open` (`src/lib/indexing.mjs`). Anything else — unset, any other value, every `staging` build, previews and manual runs from another ref — is closed: `noindex, nofollow` on every page and `robots.txt` = `User-agent: *` / `Disallow: /`.

- `.github/workflows/deploy-pages.yml` sets `SITE_INDEXING` to `open` only for a push to `main` **and** only when the repository variable `SITE_INDEXING` is exactly `open` (Settings → Secrets and variables → Actions → Variables). Opening or closing production is that one variable plus a re-run of the `main` workflow; rollback is setting it to anything else (or deleting it) and re-running.
- `src/components/BaseHead.astro` derives `SITE_WIDE_NOINDEX` from that switch; a page can only *add* `noindex` (`<BaseHead noindex />`: 404, search, and any landing page with no entries — `/research/ai-systems/` today, route-only `/research/memos/`), never remove it.
- `src/pages/robots.txt.js` generates `robots.txt` from the same switch (open: `Allow: /` + the production `Sitemap:` line). The sitemap (`astro.config.mjs` → `inSitemap()`) lists only indexable pages.
- `public/_headers` sends `X-Robots-Tag: noindex, nofollow` on every Cloudflare-owned hostname (`https://:project.pages.dev/*`, `https://:version.:project.pages.dev/*` — the staging alias and previews), never on `amulbham.com`.
- `scripts/validate-indexing.mjs` (run by `npm run build`) fails the build if the page meta, `robots.txt`, sitemap and `_headers` disagree.
- **PDF preservation (T22.0)** — `scripts/carry-over-pdfs.sh`, driven by repository variables, keeps the five scholarly PDFs byte-identical to the approved production bytes (Vivliostyle output is not byte-reproducible, and the Desk PDF on Zenodo must equal the file the site serves). `PDF_MANIFEST` (five `sha256sum` lines) + `PDF_CARRY_OVER=true` make every `main` deploy carry the live PDFs over and verify them before and after the upload. A fail-closed guard (first workflow step on `main`) stops any `main` deploy before it builds when a manifest exists but carry-over is off, unless `PDF_RELEASE=new-version` — the only value that authorizes regeneration, and only for a new Zenodo version or a new paper, never for replacing the bytes behind an already published version. Once set at launch these variables stay set; a manuscript/PDF change uses the release procedure in `planning/tickets/T22.0-public-mvp-launch.md`, and a revised already-published paper ships through the frozen-artifact path below (T23.0; flow in `PUBLISHING.md` "Revising a published paper"). One-time exception (T22.0 Amendment A): the Desk's approved artifact is its published Zenodo deposit (record 10.5281/zenodo.23328158), so `carry` may fetch that single pinned file when production's Desk PDF does not already match the manifest; the manifest hash still gates every byte, and no other path has an alternate source.
  - **Frozen artifact for a revised paper (T23.0).** A revised paper's PDF cannot come from production, which still serves the old bytes. `carry` may install exactly one hash-named file per run from `site/release-pdfs/<sha256>.pdf`, only when all three agree: the owner-set `PDF_MANIFEST` line for that path, the committed blob (which must hash to its own name and be a PDF), and the committed release expectation `site/release-pdfs/expected.txt` (manifest-format lines naming the same path and hash). `guard` (first step, every mode including `PDF_RELEASE=new-version`) and `carry` fail closed when `expected.txt` exists and `PDF_MANIFEST` does not contain every expectation line, so a revised article cannot deploy under a manifest that still names the old PDF. A path whose production copy already matches the manifest is never swapped: the transition run performs one swap and every later run zero. `PDF_CARRY_OVER` stays `true` throughout; the owner sets the new manifest line immediately before the release push.

**Do not set the repository variable `SITE_INDEXING` to `open`, or change this mechanism, without the user explicitly asking for it** — the launch sequence, verification matrix and rollback are in `planning/tickets/T22.0-public-mvp-launch.md`. Never open staging.

## Design system

**Visual contract: `site/design-system/`** (`README.md`, `tokens.md`, `components.md`, `do-not.md`). Do not invent color, type, or chrome that isn't in that folder. Content pipeline rules (frontmatter, citation conventions, routing, deploy discipline) stay in this file — that folder is visual only.

- **Tokens**: `src/styles/global.css`. Semantic color tokens (`--bg`, `--text-primary`, `--text-secondary`, `--accent`, `--border`, etc.) with a `:root[data-theme='dark']` override block plus a `@media (prefers-color-scheme: dark)` fallback for users who haven't made an explicit choice. Also: spacing (`--space-1`…`--space-8`), radius (`--radius-sm/md/lg/full`), a modular type scale (`--text-xs`…`--text-4xl`), two content-width tokens (`--content-width-prose` 720px for reading columns, `--content-width-wide` 960px for grids/listings), and per-category accent colors (`--pillar-{category}` — the token prefix predates the category registry and was kept, T19.0 — muted tints via `color-mix()`, not full-saturation fills) plus admonition-severity colors (`--alert-*`). **Every color token needs an explicit dark-mode value in both the `:root[data-theme='dark']` block and the `@media` fallback** — `--pillar-*`/`--alert-*` shipped without one for a while (a real bug, found 2026-08-20: `--pillar-ai-systems` was the exact same hex as light mode's `--accent`, which itself needed a brighter dark-mode value to stay legible; pillar/alert colors never got the same treatment, so badges and admonitions read muddy in dark mode while everything else looked fine). Check both blocks when adding a new color token, not just one.
- **Dark mode**: `ThemeToggle.astro` (vanilla JS, no framework) toggles `data-theme` on `<html>` and persists to `localStorage`. `BaseHead.astro` has a render-blocking inline script that applies the stored preference before first paint (no flash) — this same function **also runs on `astro:after-swap`**, not just once on initial load, since Astro's `<ClientRouter />` swaps `<head>`/`<body>` on every internal navigation to match the destination page's static HTML, which never has `data-theme` baked into it (only this script ever adds it). Without the `astro:after-swap` re-run, toggling dark mode then clicking any internal link silently reverted to light — a real bug, found and fixed 2026-08-20. The toggle's click handler is bound via event delegation on `document`, not the button directly — View Transitions swaps/recreates the header on every client-side navigation, so a handler bound to the button itself would silently stop working after the first navigation.
- **Fonts**: two families only (deliberately not three — keeps it "restrained"). Atkinson Hyperlegible for body *and* headings (bold weight for headings, no separate display face). IBM Plex Mono reserved strictly for metadata: dates, tags, breadcrumbs, category labels, code blocks — anywhere the `.meta` utility class is used. Both are declared in `astro.config.mjs`'s `fonts` array *and* must be rendered via `<Font cssVariable="..." />` in `BaseHead.astro` — declaring a font in config without rendering it via `<Font>` silently does nothing (`var(--font-mono)` just falls back to generic `monospace`).
- **Shared components** (`src/components/`): `Button` (primary/secondary/ghost, renders `<a>` or `<button>`), `Card` (bordered list-item wrapper; exposes `--card-hover-color` custom property so slotted headings can react to card hover without needing `:global()` — Astro's CSS scoping means a parent's `<style>` can't target a child component's elements by tag name), `Badge` (neutral, or category-tinted via `variant="pillar"` + a `category` prop — every card shows its entry's editorial category (T19.0); `variant="neutral"` is for generic tags; the pillar variant also gets a subtle tinted border, `color-mix(... 20%, transparent)` of the same `--badge-color`, one step darker than the 12% tint used for the background), `Breadcrumbs`, `RecentResearch` (self-contained: fetches + renders `research` entries across all formats — by default the 3 most recent as cards (the 404 page); the opt-in `variant="feed"` (T21.0) is the homepage's single-column list of up to five entries excluding the spotlight, `pubDate` descending with an entry-id tie-break, nothing rendered when empty), `RelatedResearch` (up to 3 entries sharing the current one's category and/or tags — the category bonus applies to every category except `essays`, an editorial catch-all rather than a topical cluster; `relatedBonus` in `categories.ts`), `SocialLinks` (footer only — deliberately not in the header, which stays limited to primary nav + search + theme toggle; reads from `SOCIAL_LINKS` but only renders these three via its own local `links` array, so adding a new key to `SOCIAL_LINKS` — e.g. `orcid` — does not automatically add a footer chip. Renders as mono-font bordered text-abbreviation chips (`in`/`S`/`</>`), not icons — this site deliberately has no icon library, per the design system imported 2026-08-24), `ThemeToggle`, `TableOfContents` (sticky rail with scroll-spy, gated behind a heading-count threshold — see below; the active/hovered link also gets a left accent border, not just a color change), `ScrollProgress` (fixed bar at the top of the viewport, fills with scroll position on every research page — rendered once inside `ArticleShell.astro`, so `ResearchLayout` gets it automatically with no per-layout wiring; no heading-count gating, unlike the TOC, since it's cheap even on short pages).
- **Article masthead**: `ArticleMasthead.astro`, rendered by `ResearchLayout.astro` at the top of the `after-title` slot (same slot tags/pdf-link already occupy). Renders name/affiliation/correspondence/format/license entirely from `AUTHOR`/`LICENSE`/`SOCIAL_LINKS` in `consts.ts` plus the existing `formatLabel()` helper — **no frontmatter needed**, since this data is identical on every entry by a solo author. Added 2026-08-24 specifically because the equivalent content used to be hand-typed Markdown in each article's body, and two early pieces had already drifted into different formats from each other within days — see `CHANGELOG.md`. If a new piece ever has hand-typed byline content in its body, that's a bug to fix (delete it, let the component render it), not a style choice.
- **Header logo**: `Header.astro` renders the "AB" geometric ligature mark (v2, replacing the original design-system serif+dots monogram same-day 2026-08-24 — a flat two-tone shape scales to favicon sizes far better) as **two** assets, `logo-header-light.png`/`logo-header-dark.png` (`src/assets/`, imported via Astro's `<Image>`), toggled by CSS using the exact same `[data-theme='dark']`/`prefers-color-scheme` guard pattern as every color token in `global.css` and `ThemeToggle.astro`'s own sun/moon icon swap — not a single raster image, since the mark needs to flip color with the theme. `alt=""` on both — the adjacent site-title text already names the site, a redundant alt would just repeat it. - **Table of contents**: only renders when an entry has **6 or more `##` headings** (`MIN_SECTIONS = 6`, `TableOfContents.astro`) — measured against real papers, not guessed, and confirmed still correct at every point it could have been reconsidered (scroll-spy's addition, Sprint 10's rewrite). Only `##`-level headings are surfaced (not `###`). `TableOfContents.astro` takes a `variant` prop (`'rail' | 'mobile' | 'both'`, default `'both'`) — `ResearchLayout.astro` renders it twice, once per variant, into `ArticleShell.astro`'s separate `toc` (desktop sticky rail, **`≥1100px`**, unchanged breakpoint) and `mobile-toc` (the same native `<details>`, **`<1100px`**) slots.

  **Reading-shell invariants, frozen Sprint 10.6 (10.0–10.5 built this; nothing here is up for casual revision):**
  - **Exactly one `IntersectionObserver`, ever** — lives in `ArticleShell.astro` (not `TableOfContents.astro`, since that component renders twice per page and a script inside it would run twice). No scroll event listener, no polling, no `MutationObserver`. Its callback ignores its own entries and just re-runs the same `syncCurrentSection()` viewport calculation init already uses, so cold start, a direct `#hash` load, a View Transitions landing, and normal scrolling can never disagree about what "current" means.
  - **One shared current-section state**, not two independent ones: `setCurrentSection(slug)` is the single place that writes `.active`/`aria-current="location"` to both the desktop rail and the mobile list, and swaps the mobile summary between its section-count and current-title spans. `slug === null` means "above the first heading."
  - **`ACTIVE_ZONE_FRACTION` (`0.3`, i.e. the top 30% of the viewport) is the one source both the observer's `rootMargin: '0px 0px -70% 0px'` and the manual viewport-sync calculation derive from** — defined once so the two numbers can't silently drift apart from each other.
  - **`AuthorNote` can never become TOC/current-section state** — it isn't part of either link set (`[data-toc-link]`/`[data-toc-mobile-link]`) the shared model is built from, so this holds by construction, not by a special-case check. The last real `##` heading stays "current" all the way through `AuthorNote`/`RelatedResearch`, since nothing after it can out-rank it in the activation-band calculation.
  - **`--toc-mobile-offset` (`global.css`, next to `.toc-mobile`) must stay `rem`-based, never `em`.** A CSS custom property is a token sequence, not a resolved value — its units get evaluated wherever the property is actually *consumed*. This variable is consumed as `scroll-margin-top` on each `h2`, so an `em` inside it resolves against that `h2`'s own (much larger) font-size, not the small TOC bar the number is meant to describe — a real bug shipped in 10.3 and only fixed in 10.4 once someone asked *why* the already-measured ~83px overshoot was happening rather than treating it as an acceptable margin. `rem` is anchored to the root font-size regardless of which element consumes it, so it can't inherit this class of bug. Scoped to `<1100px` only (`@media (max-width: 1099px)`) — no desktop offset exists, since the rail sits beside the prose there, not above it.
  - **Mobile link taps defer closing `<details>` by one tick (`setTimeout(fn, 0)`), not synchronously** (Sprint 10.5) — closing it in the same event as the anchor's own hash navigation raced `<details>` hiding its content against `ClientRouter`'s same-page anchor handling, silently dropping the hash update. `setCurrentSection()` itself stays synchronous (pure class/attribute toggling, no such race).

  Reinitializes on `astro:page-load`, not `DOMContentLoaded`, following the same View Transitions pattern as Pagefind's init in `search.astro`.

### Content-section transforms — standing policy

Recurring content-section patterns (References today; others as they actually recur — don't pre-build for sections that don't exist yet) get a **build-time remark/rehype transform**, registered in `astro.config.mjs`'s `markdown.processor: unified({ remarkPlugins, rehypePlugins })`. Not MDX, not hand-written components in content files. This is a deliberate policy, not just how it happened to get built: it means authoring stays plain Markdown — paste it exactly as before, the transform recognizes known section shapes and styles them automatically. Reserve MDX/real components for anything that genuinely can't be expressed as plain Markdown (real interactivity, data that doesn't fit a list/table shape) — nothing on this site needs that yet.

**The full contract for every module — trigger, produces, authoring example, constraints, files — lives in `CONTENT-MODULES.md`, not here; don't paste individual contracts into this file.** That includes `rehype-research-primitive.mjs` (added Sprint 2, 2026-08-26): five shape-triggered `<aside>` kinds — definition, key-idea, evidence, counterpoint, implication — from a bolded blockquote label. Visual chrome (tokens, component styling) → `design-system/`. Content modules (what Markdown shape triggers what structure) → `CONTENT-MODULES.md`. The list below is kept only for the parts of the picture `CONTENT-MODULES.md` doesn't own (registration gotchas, npm-package exceptions, unscoped-CSS rationale) — when the two disagree on a fact, `CONTENT-MODULES.md` is authoritative for the module's contract.

All registered together in `astro.config.mjs`'s `markdown.processor: unified({ remarkPlugins: [remarkReadingTime, remarkAlert], rehypePlugins: [rehypeReferences, rehypeTableWrap, rehypeFigures, rehypeKeyFindings, rehypePullQuote, rehypeResearchPrimitive, rehypeCitationLinks, rehypeHeadingIds, rehypeResearchLinks] })`. All are hand-rolled, zero-dependency plain functions in `src/lib/`; `remarkAlert` is a deliberate exception to that — see below.

**Standing pipeline invariants for `rehype-research-links.mjs` (Sprint 7.5, 2026-09-01 — frozen 7.8)**:

- **Order is load-bearing: `rehypeCitationLinks` → `rehypeHeadingIds` → `rehypeResearchLinks`.** `rehypeHeadingIds` (imported from `@astrojs/markdown-remark`) has to be listed explicitly, positioned right before `rehypeResearchLinks`. Astro's own default heading-id assignment isn't part of this project's `rehypePlugins` array at all by default — the `unified()` config wrapper this project uses appends it unconditionally *after every plugin in that array*, once, at the very end of the real pipeline (confirmed from `@astrojs/markdown-remark`'s own `createMarkdownProcessor`). That's fine for every other plugin here, none of which read heading ids — but `rehypeResearchLinks` needs `id="..."` to already exist to resolve a relation's `inline.near`. Including `rehypeHeadingIds` here runs it a second, harmless time (it only assigns an id when one isn't already set); Astro's own automatic pass still runs again afterward regardless.
- **Never call `getEntry`/`astro:content` from inside a rehype plugin.** Confirmed by a real build failure, not assumed: `astro:content` is a Vite virtual module, unreachable from the plain-Node context a markdown rehype plugin runs in (`Only URLs with a scheme in: file, data, and node are supported`). A relation's target path is always resolved as `canonicalPath()` (from `research-routing.ts`) called on an object built from the target's own frontmatter (read directly via `parseFrontmatter`) — never a hand-built `/research/{category}/{id}/` string, and never an `astro:content` import from this layer.
- **A plugin throw alone is not the fail-closed gate — `scripts/validate-research-links.mjs` is.** Also confirmed directly: Astro's own content-layer glob loader catches a per-entry markdown render error, logs it, and *continues* — `astro build` exits 0 regardless, with the affected page silently missing content. `scripts/validate-research-links.mjs` runs the identical pipeline standalone, with no surrounding try/catch, and is the first step of `npm run build` (`tsx scripts/validate-research-links.mjs && astro build && pagefind --site dist`) specifically so the same failure is a real non-zero exit. Do not remove it from that script, and do not treat the plugin's own `throw` as sufficient on its own.

**Standing invariants for the research-relation semantic-projection layer (Sprint 11.3/11.4, permanently enforced by Sprint 11.7):**

- Never infer a Schema.org property from a canonical relation's `type` (no `RELATION_SCHEMA_MAP`, no `switch` on `type`) or from `relation.reason` prose (no keyword/regex/LLM inference). Projection is edge-level and human-authored: `research-relation-projections.json`'s `relationId` foreign key is the only mechanism, and it names one specific edge, never a type or a pattern.
- `research-relations.json` = the canonical intellectual graph (registry presence = accepted relation). `research-relation-projections.json` = the explicit external projection policy — a separate registry, never redefining `source`/`target`/`type`/`reason`.
- `inline.status` governs only whether a relation manifests as an in-body HTML link. It must never gate semantic-projection eligibility, and semantic projection must never be inferred from it — three independent axes (canonical existence, inline manifestation, semantic manifestation), none implying another.
- `src/lib/research-relation-projections.ts` must stay plain-Node compatible — never import `astro:content` — since it's loaded both by plain-Node validators (`validate-research-relation-projections.mjs`, `validate-research-semantics.mjs`, via `tsx` outside Vite's module graph) and by `ResearchLayout.astro`. Target-entry resolution (`getEntry`) belongs only in the real Astro/Vite layer (`ResearchLayout.astro`), never in this shared module — the same `astro:content`/plain-Node boundary already established above for `rehype-research-links.mjs`.

**Four validators, four different boundaries, do not conflate them (Sprint 8.6, extended 11.3/11.7).** `scripts/validate-research-relation-projections.mjs` protects source projection-config integrity (schemas, uniqueness, referential integrity) — runs first, before `astro build`. `scripts/validate-research-links.mjs` is a markdown-content gate — it runs *inside* `npm run build`, before `astro build`, on every push including Cloudflare's own native build. `scripts/validate-research-semantics.mjs` protects the emitted Schema.org graph — it runs *after* `astro build`, before Pagefind, against built `dist/` HTML (see the standing invariants above). It also checks category navigation (T19.0): the footer lists the registered categories in registry order and the homepage links its spotlight (the homepage has no category grid since T21.0), every `/research/{segment}/` link resolves to a built page, and route-only `/research/memos/` never appears in navigation. `scripts/validate-research-pdfs.mjs` (`npm run validate:pdfs`) is a Scholar/PDF-identity gate — it only makes sense **after** `npm run build:pdfs` has actually produced PDFs to check, so it runs as its own step in `.github/workflows/deploy-pages.yml`, between `build:pdfs` and `wrangler pages deploy`, and is deliberately **not** added to `npm run build` itself (Cloudflare's native build never produces PDFs — see "Transitional as of Sprint 8.2" above — so there'd be nothing for it to check there, and it would just fail every push). It discovers papers via the shared `scripts/discover-research.mjs` (also used by `build-research-pdfs.mjs`, so there is exactly one paper-discovery implementation, not two that can drift), parses each paper's canonical `{entry.id}.pdf` (filename from `paperPdfFilename(id)`) with `pdfjs-dist` (pinned exact version, never a raw-bytes/compressed-stream grep — see `CHANGELOG.md`'s Sprint 8.6 entry for why a real parse is load-bearing), fails closed on a physical `paper.pdf`, a `dist/_redirects` that differs from the set `route-history.ts` generates (written by `build:pdfs`: each paper's legacy `paper.pdf` 301 plus every retired public route of a moved entry — T18.1, T19.0), or a route-history violation (see "Route history" under Content) or a page-1 masthead ORCID (derived from `SOCIAL_LINKS.orcid`) split across lines (T18.2), and checks identity/link-structure only — it does not re-check the visual rows (table rendering, page-1 layout, primitive rendering) Sprint 8.5 already established stay a human raster check. `scripts/lib/built-html.mjs` (Sprint 11.7) holds the built-HTML extraction primitives (`decodeEntities`, `extractJsonLdBlocks`, `extractCitationMeta`, `findArticleLikeJsonLd`, `extractCanonicalHrefs`) shared by the semantic and PDF validators — PDF-specific extraction (`.pdf-link` href, `#ref-N` reachability, `data-relation` link harvesting, PDF parsing itself) stays local to `validate-research-pdfs.mjs`, which remains the only consumer.

Finding the object is never the same check as validating its type: `validate-research-semantics.mjs` separately asserts the intentional v1 contract (paper: `@type` contains both `ScholarlyArticle` and `Article`; essay/memo: `@type` is exactly `Article`) against whatever the locator finds. Do not change `ResearchLayout.astro`'s actual emitted `@type` merely because the locator can now recognize `ScholarlyArticle` alone — the explicit `"Article"` stays part of the intentional paper output contract.

**`SITE_ORIGIN`/`DEFAULT_ORIGIN` is a hand-synced literal, not a single source of truth — check all three before changing the production origin.** `astro.config.mjs`'s `site:` field is the real origin, but it isn't safely importable from a plain `tsx` script (running Astro's own integration setup at import time, which assumes a real Astro/Vite context these scripts don't have) — so `scripts/absolutize-pdf-links.mjs`'s `DEFAULT_ORIGIN` (Sprint 8.1) and `scripts/discover-research.mjs`'s `SITE_ORIGIN` (Sprint 8.6, re-exported for `validate-research-pdfs.mjs`) are both separately declared literals, kept in sync by hand. If `amulbham.com` ever changes, all three need the same edit — a mismatch here would silently break `validate:pdfs`'s identity checks against a domain that no longer matches the real one.

- `remark-reading-time.mjs` — operates on the **mdast** (markdown AST, before HTML conversion), computes `wordCount`/`minutesRead` into `remarkPluginFrontmatter`.
- `rehype-section-utils.mjs` — shared factory, `createHeadingSectionWrapper({ headingText, sectionClass, listTags, onWrap })`, extracted from `rehype-references.mjs` once a second heading+list transform (`rehype-key-findings.mjs`) needed the identical detection logic. Operates on the **hast**. Restructuring/wrapping actual elements is a rehype job, not remark — mdast has no clean way to express an arbitrary wrapper element. **Gotcha already hit once**: the heading and list are *not* strictly adjacent siblings in the tree — there's a whitespace-only text node (a literal `"\n"`) between them from the blank line in the source Markdown, so this skips whitespace text nodes when looking for "the next real sibling," not assume `children[i + 1]` is it.
- `rehype-references.mjs` — `createHeadingSectionWrapper({ headingText: 'references', sectionClass: 'references', listTags: ['ol'] })`. Restricted to `<ol>` only (unlike Key Findings, which also accepts a bullet list) since the `onWrap` callback assigns each `<li>` a stable `id="ref-N"` (1-based document order) — this only makes sense for a numbered reference list.
- `rehype-key-findings.mjs` — `createHeadingSectionWrapper({ headingText: 'key findings', sectionClass: 'key-findings' })`. Wraps a "Key Findings" heading + list (ordered or unordered) in `<section class="key-findings">`, styled as a highlighted callout box in `global.css` (reusing the `.pillar-card` visual language already live on `/about`, not a new treatment). Entirely opt-in — a paper without that heading renders nothing extra.
- `rehype-table-wrap.mjs` — operates on the **hast**, wraps every `<table>` (walking the whole tree, not just top-level children — unlike `rehype-references`, tables can appear inside list items) in `<div class="table-container" tabindex="0">`, styled with `overflow-x: auto` in `global.css` so wide tables scroll horizontally on narrow viewports instead of breaking `--content-width-prose`.
- `rehype-figures.mjs` — operates on the **hast**, walking the whole tree. Promotes a `<p>` whose only meaningful child is an `<img>` (the shape standard `![alt](src)` Markdown always produces — confirmed against Astro's actual built-in markdown image optimization output, not assumed) into `<figure><img/><figcaption>{alt}</figcaption></figure>`. Skips the `<figcaption>` entirely when alt text is empty, so a captionless image doesn't get an empty caption box — there's no separate flag for "has a caption," it's purely alt-text-driven.
- `rehype-pull-quote.mjs` — operates on the **hast**, walking the whole tree. Promotes a `<blockquote>` whose entire content is a single bolded line (`> **Not a score. A dependency.**`) into a large-type, centered "pull quote" (`class="pull-quote"`) for visual rhythm in long-form text — a restated key line, duplicated from the body, not a new sentence. Doesn't collide with GFM alerts: those are consumed by `remarkAlert` during the **remark** phase, so by the time this rehype plugin runs they're already `<div class="markdown-alert...">` elements, not blockquotes at all. Ordinary citation blockquotes are unaffected too — their content isn't a single whole-line `<strong>`, so the shape check excludes them. Added 2026-08-20 for the frontier-model essay, which read as too text-dense without any visual breaks.
- `rehype-citation-links.mjs` — **must run after `rehype-references.mjs`** (reads the `id="ref-N"` values it assigns). Auto-links inline citations to their reference-list entry: `(Bennett, 1987)` → `<a href="#ref-1">`. Built 2026-08-19 once real content confirmed every inline citation actually maps to a reference — this was previously deferred as "real text-parsing work, do it later" (see `CHANGELOG.md`), and real content turned out to need **two** citation shapes, not the one originally anticipated:
  - **Parenthetical** — `(Name, Year)`, including semicolon-separated multi-source groups `(Name1, Y1; Name2, Y2)` (each sub-citation linked individually, `(`/`;`/`)` left as plain text), and `(Name, n.d.)`. Matched by extracting the name from inside the already-paren-bounded group, then looking it up — safe because the literal `(`/`)` naturally bound where the candidate name starts and ends.
  - **Narrative** — `Name (Year)`, e.g. `Macartney et al. (2024)`, `O'Brien v. Weinberger (1978)` (a distinct legal-citation sub-shape: `Case Name v. Other Name (Year)`, `year` read from inside that specific parenthetical, not the first 19xx/20xx digit anywhere in the reference — a court citation's reporter/page numbers could otherwise be misread as the year). **Bug found and fixed while building this**: matching this shape against a *generic* capitalized-phrase pattern (`[A-Z][A-Za-z... ]+\(Year\)`) is unsafe — its leftmost-match preference grabs whatever capitalized text starts the enclosing sentence (`"As documented in Macartney et al. (2024)"` matched as the whole "name", not just `"Macartney et al."`), since unlike the parenthetical shape there's no literal `(` bounding where the name starts. Fixed by matching against the *known* reference names directly (an escaped regex alternation of every name already in the lookup table, sorted longest-first) instead of a generic pattern.
  - **Second bug found and fixed**: Astro's markdown pipeline smartypants-converts straight quotes to curly ones (`'` → `’`) before this plugin sees the text. The parenthetical shape's Map-based lookup already normalized this correctly on both sides; the narrative shape's regex *pattern* (built from already-normalized straight-quote lookup keys) didn't account for curly quotes in the *searched* text, silently failing to match `O’Brien v. Weinberger`. Fixed by searching a straight-quote copy of the text (same length, so match indices stay valid) while still slicing the final linked substring from the original text, preserving the curly quote actually rendered.
  - Fails closed throughout — anything that doesn't resolve to exactly one reference stays plain text. Verified against every one of the financial-aid paper's real inline citations (45 links, individually cross-checked against the 35-entry reference list) before shipping, not spot-checked.
  - **Third round of bugs found and fixed 2026-08-24**, stress-testing against a real 32-reference cross-disciplinary paper with citations back to 1850: (1) `extractReferenceKey` only ever registered a reference's *first* author as its lookup key, so a two-author entry ("Nicolis, G. & Prigogine, I.") couldn't match either its parenthetical `&` form or its narrative `and` form (real APA style uses `&` in parentheses, `and` in prose — both need to resolve) — fixed by also registering `"surname1 & surname2"` and `"surname1 and surname2"` as keys whenever a reference entry has exactly two authors. (2) The surname-detection regex used `[a-zA-Z]`, so a two-word surname ("Conway Morris", "Maynard Smith") or an accented one ("Poincaré", "Szathmáry") silently failed to match at all — fixed with a Unicode-aware `\p{L}` character class (`/u` flag) instead of an ASCII range. (3) The year regex was hardcoded to `(19|20)\d{2}`, meaning *any* pre-1900 citation was structurally unmatchable — not a deliberate bound, just never tested against content old enough to hit it — widened to `(1[6-9]|20)\d{2}`. All three were real, generalizable gaps, not this-paper-only fixes. **What still fails closed by design, not a bug**: citing the same author's multiple works together in one group, comma- or semicolon-separated (`Kauffman (1969; 1993)`, `Clausius (1850, 1865)`) — only the first year links, since the trailing year has no name directly attached and the system correctly declines to guess rather than risk linking it to the wrong entry.
- `remark-github-blockquote-alert` (npm package, not hand-rolled) — parses GFM alert syntax (`> [!NOTE]`, `[!TIP]`, `[!WARNING]`, `[!CAUTION]`, `[!IMPORTANT]`) into `<div class="markdown-alert markdown-alert-{severity}">` blocks. The one deliberate exception to "hand-roll it" in this policy: parsing multi-paragraph blockquote alerts correctly (nesting, multiple body paragraphs) has more edge cases than the References/table wrappers, and this package already handles them, is actively maintained, and adds a single small transitive dependency (`unist-util-visit`). Its default GitHub-styled CSS is **not** imported — `global.css` re-themes the `.markdown-alert*` classes with this site's own tokens (`--alert-note/tip/important/warning/caution`, same muted-tint `color-mix()` treatment as `--pillar-*`) so it stays consistent in dark mode.

Section-transform CSS (`.references*`, `.table-container`, `.markdown-alert*`, `figure`/`figcaption`, `.key-findings*`) goes in `global.css`, unscoped — same reason `.prose p`/`code`/`pre`/`blockquote` are unscoped there: Astro's component-scoped `<style>` can't reach markup injected via `<slot />` from rendered Markdown, only markup written directly in that `.astro` file's own template.

## Content

- **One collection, three formats**: `src/content.config.ts` defines a single `research` collection, distinguished by a `format: 'paper' | 'essay' | 'memo'` field. Unified 2026-08-20 from what were previously two separate collections (`papers`, `blog`) with separate schemas/layouts/routes — the split turned out to cost more in duplicated maintenance (two layouts to update every time a shared feature landed, two index pages, two route trees) than it bought, and fragmented the reader-facing browsing experience across `/research-hub/` and `/blog/`. **`paper`**: rigorous, protocol-driven research; gets a scholarly PDF, Highwire tags and `ScholarlyArticle` JSON-LD in any category (T19.0 — FAFSA is a paper placed in Essays). **`essay`**: long-form analytical prose, plain `Article` JSON-LD. **`memo`**: shorter, more casual notes, same shape as essay — a category with room to grow into, no entries yet. Currently 4 papers (the FAFSA/financial-aid piece; "The Invariants of Self-Organizing Systems," a cross-disciplinary complexity-science paper added 2026-08-24 as the real test case for the content-manager skill — see `.claude/skills/content-manager/`; its companion, "Three Self-Organizing Systems," added 2026-08-31, the first entry to carry a real accepted research-relation row — see "New: research relations" in `CONTENT-MODULES.md`; and "The Chisel Fallacy: What Pangram Actually Measures," added 2026-09-22 at T13.2, the first Article to carry a published companion IWL — see "IWL — the Intellectual Work Ledger companion object" below) and 1 essay (on frontier model training economics); the placeholder sample content used during the initial build was removed 2026-08-19 so nothing fake gets crawled.
- **Content lives in per-slug folders**: `src/content/research/<slug>/index.md`, not flat `<slug>.md` files (so each entry can have images alongside it). The content-layer `glob()` loader strips a trailing `/index` from the generated slug (confirmed directly from Astro's source, `content/utils.js`'s `getContentEntryIdAndSlug`), so `entry.id` is unaffected by the folder structure — still the bare slug. Any image referenced from an entry's body via a relative path (e.g. `./figure-1.png`) should live in that same folder.
- **Frontmatter** — required: `title`, `format`, `pubDate`, `description`, `excerpt`. Optional `subtitle`, rendered directly under the `<h1>` by `ArticleShell.astro` — use this instead of a `##` heading in the body for a subtitle: a heading gets picked up by the TOC transform as a real section (a real bug, found and fixed 2026-08-24 — the financial-aid paper's subtitle was showing up in its own TOC, right next to "Abstract"). `category` is required on every entry (a `z.enum` over `CATEGORIES`, `src/lib/categories.ts`; the retired `pillar` key fails the build). A `doi` requires `format: 'paper'` (a schema `.refine()`, T19.0): a Zenodo-published work must carry a scholarly PDF, which only papers get. A paper may exist before it has a DOI. Optional: `tags` (defaults to `[]`), `dateModified`, `doi` (rendered in the masthead alongside the correspondence details when present), `heroImage`, `heroImageAlt`, `readerNote` (Sprint 12.1 — `{ why, for }`, `.strict()` and complete-or-absent, rendered by `FromTheAuthor.astro`; earned editorially per piece, never required, never inferred from `format`/voice — see `PUBLISHING.md`'s "research object's semantic graph" for the `for → Article.audience` machine projection). **No `pdfUrl` field** — a paper's PDF has exactly one identity, `{canonical article directory}/{entry.id}.pdf` (filename from `paperPdfFilename(id)` in `research-routing.ts`; the legacy `{canonical article directory}/paper.pdf` is a 301 to it, and a physical `paper.pdf` file is forbidden — T18.1), derived in `ResearchLayout.astro` and shared by `citation_pdf_url`, the JSON-LD `MediaObject`, and the reader-facing Download PDF link (Sprint 8.4; see `PUBLISHING.md` §5) — the same discipline `canonicalURL` itself already used, for the same reason (a hand-authored field can drift from the real route; a derived one can't). An optional `## Key Findings` heading (followed by a list, ordered or unordered) anywhere in the body gets auto-styled as a highlighted callout box — see "Content-section transforms" above. **No `canonicalURL` field** — it's derived in `ResearchLayout.astro` (via `src/lib/research-routing.ts`, see below) from the category + slug, specifically so it can never drift from the actual route (this happened once: a paper's `canonicalURL` frontmatter still said its old pillar after the `pillar` field itself was updated, silently breaking that page's JSON-LD `url` for a while).
- **`description` vs `excerpt`**: `description` is used only for the JSON-LD `description` field (schema.org has no length concern there) and is not rendered on the page. It is normally the full abstract; a paper with no abstract sets it equal to `excerpt` rather than inventing one (T23.0, the Chisel Fallacy v9). `excerpt` (`z.string().max(200)`, aim for ~155–160 chars) is the short summary used for the actual `<meta name="description">`/OG description tag and every card blurb site-wide: `RecentResearch.astro`, `RelatedResearch.astro`, `research/index.astro`, `research/[category]/index.astro`, `tags/[tag]/index.astro`, and `rss.xml.js`. Always write both — the schema has no fallback if `excerpt` is missing. (Split out 2026-08-19 after a real bug: the FAFSA paper's full ~1600-character abstract was being used verbatim as the meta tag and every listing blurb.)
- **Categories/URLs** (`src/lib/research-routing.ts`) — single source of truth for how an entry maps to a URL, so this can't drift the way `canonicalURL` frontmatter once did: `categorySegment(entry)` returns the entry's authored `category` (T19.0 — formerly a paper's `pillar`, or the pluralized `format`). `canonicalPath(entry)` builds the full `/research/{category}/{slug}/` path from that (renamed from `/research-hub/` 2026-08-24 to match the design system's route naming — free to do since nothing was indexed yet). Used by the `[category]/[slug].astro` route, `ResearchLayout`'s `canonicalURL`, the OG image route, and both index pages. Every entry lives at `/research/{category}/{slug}/`; `format` no longer shapes the route. Scripts and rehype plugins that read raw frontmatter build their routing entry with `routingEntryFromFrontmatter()`, which throws on a missing or unknown category or a retained `pillar` rather than emitting an `undefined` route. Retired public routes 301 directly to their current URL (route-history bullet below).
  - **Gotcha hit building this**: `research/[category]/index.astro` needs a landing page for every registered category — and the route-only `/research/memos/` — to always build, even with zero entries (AI Systems is empty today). Emits its own `ProfilePage` + `Person` JSON-LD, separate from the homepage's `Person`/`WebSite` schema and each entry's `author` field.
- **IWL — the Intellectual Work Ledger companion object** (Sprint 13, T13.1/T13.2): a second, deliberately distinct content collection, `iwl` (`src/content.config.ts`), not a fourth `research` format — `research`'s own "do not invent a second collection" rule (`PUBLISHING.md` §2) is about papers/essays/memos staying one shape; an IWL is a structurally different object class (subordinate, optional, three-state) and was a T13.1 decision to keep separate on purpose. Schema: `parent: reference('research')` (required, fails the build on a dangling reference — Astro's own content-reference validation pass, not a hand-rolled check), `title` (required), `publicationState: 'unpublished' | 'published'` (required, no default, never inferred from file presence/branch/date), `pubDate` (required iff published via `.refine()`), optional `dateModified` (T23.0: the last substantive revision; rendered as the shell's "Last updated", absent = no line, no JSON-LD or inner schema). `.strict()` — no `format`/`pillar`/`doi`/`tags`/`readerNote`/`author`/`license`/inner-grammar field is accepted; `AUTHOR`/`LICENSE` stay centrally owned exactly like every research entry. **One registry, not parallel truth**: `src/lib/iwl.ts`'s `getIwlRegistry()`/`getPublishedIwlForParent()` is the single place that loads the collection, resolves every parent, and enforces one-IWL-source-per-parent across *all* publication states (not just published — an unpublished entry can still collide) — the IWL route and `ResearchLayout.astro`'s Article→IWL navigation both consume this same function, never an independent lookup. **Route**: `src/lib/research-routing.ts`'s `iwlPath(parent)` = `canonicalPath(parent) + 'iwl/'`, extending (never duplicating) the existing routing authority; the actual page is `src/pages/research/[category]/[slug]/iwl.astro`, a distinct file coexisting with the sibling `[slug].astro` — Astro's router treats a dynamic-segment folder and a dynamic-segment file of the same name as independent routes, so `/research/{category}/{slug}/` and `/research/{category}/{slug}/iwl/` never collide. Public paths are generated only for `publicationState: 'published'`; the registry still validates the *complete* collection first, so a malformed or duplicate unpublished entry can't hide from validation. **Layout**: `src/layouts/IwlLayout.astro`, deliberately plain — reuses `ArticleShell`/`BaseHead`/`Breadcrumbs`/`TableOfContents`/the ordinary Markdown pipeline, never `ResearchLayout.astro` itself (that layout owns Article-only semantics: `Article`/`ScholarlyArticle` JSON-LD, DOI/Highwire, Reader Context, `AuthorNote`, `RelatedResearch`, relation projections). **Emits zero JSON-LD** — T13.1's frozen decision is deliberate semantic silence for Article↔IWL (no `hasPart`/`isPartOf`/etc.), matching the `backstory` precedent; do not add one without a new, separately-earned ticket. **No PDF** — `build-research-pdfs.mjs`'s `discoverPapers()` only ever sees `format: 'paper'` `research` entries, so an `iwl` entry is structurally invisible to the PDF pipeline already, with zero extra code. **No Pagefind special-casing** — a published IWL is indexed exactly like any other built page (no per-page opt-out mechanism exists anywhere in this codebase); absent/unpublished IWLs are never indexed simply because they're never built. **Navigation**: Article→IWL is a conditional link in `ResearchLayout.astro`'s existing `after-title` region (same seam as masthead/tags/PDF link — never a new `ArticleShell` slot, and never the `reader-context` seam Sprint 12 reserved for non-metadata content); IWL→Article is an explicit "Companion to: `<title>`" line near the top of `IwlLayout`. Both directions derive from the registry at build time — `research` frontmatter never gains a reciprocal `iwlId`/`iwlUrl`/`hasIwl` field. **Licensing**: an IWL page renders the sitewide `LICENSE` constant exactly like a research entry; there is no per-IWL license field, so a source `.docx`/draft's own license text (if any) must be reconciled away during conversion, not preserved. Full rationale for every decision above: `planning/tickets/T13.1-iwl-outer-contract-decision.md`'s Final Decision Record and `planning/tickets/T13.2-iwl-outer-envelope-implementation.md`'s completion report. Inner IWL grammar (the four authored surfaces, any node/edge/epistemic-status vocabulary) is explicitly **not** schema — it is prose-first authored Markdown. OPAQUE V1, accepted at T15.1: no inner machine schema was earned for the current Research Object MVP.
