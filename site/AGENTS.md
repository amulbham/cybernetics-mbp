# cybernetics-mbp

Personal research hub for Amul Bham (amulbham.com) — Astro 7, static output, deployed on Cloudflare Pages. This file auto-loads every session. **At the start of new work, read `ROADMAP.md` for pending items and `CHANGELOG.md` for recent history** — both are real files in this repo, not auto-loaded, so they have to be opened deliberately.

## Development

```sh
astro dev --background
```

Manage with `astro dev stop`, `astro dev status`, `astro dev logs`. Search (`/search`, Pagefind) and OG images only work against a built site — `astro dev` can't serve either. To test them: `npm run build && astro preview`.

**If you change the markdown pipeline (add/edit a remark or rehype plugin in `astro.config.mjs`) and the build doesn't reflect it**: clear `node_modules/.astro/` (its `data-store.json` is a content-layer cache, separate from `.astro/` and Vite's cache, and it can silently keep serving previously-rendered HTML even after `dist`/`.astro` are cleared). This cost real debugging time once already — `rm -rf node_modules/.astro dist .astro` before rebuilding if a markdown-pipeline change doesn't seem to be taking effect.

## Deploy workflow — staging → production

- **`main`** is production. Cloudflare Pages watches it and auto-deploys to `amulbham.com` on every push.
- **`staging`** is the working branch. Every push gets its own live Cloudflare Pages preview build, fully isolated from production. Stable branch alias: `https://staging.cybernetics-mbp-site.pages.dev/` (always reflects the latest push to `staging`; per-commit preview URLs like `https://<hash>.cybernetics-mbp-site.pages.dev/` also exist but change on every push).
- **Day-to-day**: do work on `staging`, push, check the preview, iterate as many times as needed — nothing reaches `amulbham.com` until `staging` is merged into `main`. Merge via GitHub PR (`github.com/amulbham/cybernetics-mbp/pull/new/staging`) or a direct `git merge staging` into `main` — either way, verify the live preview *before* merging and re-verify production *after*, since a merge triggering a build isn't the same as confirming the build actually shipped what you expect.
- Cloudflare Pages project settings: root directory `site` (the repo root isn't the Astro project), build command `npm run build` (this already includes the Pagefind indexing step — see below), output directory `dist`, Node 22+.
- **When polling a preview/production URL to confirm a deploy landed, check for a marker that's only true on the *new* build — not just present on both old and new.** A `grep -q "some string"` check that's already true on the previous deploy will report "live" immediately without the new build having actually shipped (hit this for real: checking for `"function initToc"` passed instantly because the *old, buggy* build already contained that string too — just twice instead of once — so the fix's absence went unnoticed until the actual occurrence *count* was checked). Also add a cache-busting query param (`?cb=<random>`) when re-checking after a fix — Cloudflare's edge cache can keep serving stale HTML for a bit past when the new build actually finished.

## Indexing state — READ BEFORE TOUCHING

The site is **deliberately deindexed** while content/design work continues:

- `public/robots.txt` → `Disallow: /`
- `src/components/BaseHead.astro` → `const SITE_WIDE_NOINDEX = true;` forces `noindex, nofollow` on every page via the `<SEO/>` call, regardless of environment (staging and production both stay deindexed).
- Individual pages can still force `noindex` themselves via `<BaseHead noindex />` regardless of the site-wide flag (used by `404.astro`, since a 404 should never be indexed even after launch).

**Do not flip `SITE_WIDE_NOINDEX` to `false` or restore `robots.txt` to `Allow: /` without the user explicitly asking for it.** When they do: flip both together (they were designed as one change), and restore the `Sitemap: https://amulbham.com/sitemap-index.xml` line in `robots.txt` at the same time.

## Design system

- **Tokens**: `src/styles/global.css`. Semantic color tokens (`--bg`, `--text-primary`, `--text-secondary`, `--accent`, `--border`, etc.) with a `:root[data-theme='dark']` override block plus a `@media (prefers-color-scheme: dark)` fallback for users who haven't made an explicit choice. Also: spacing (`--space-1`…`--space-8`), radius (`--radius-sm/md/lg/full`), a modular type scale (`--text-xs`…`--text-4xl`), two content-width tokens (`--content-width-prose` 720px for reading columns, `--content-width-wide` 960px for grids/listings), and per-pillar accent colors (`--pillar-*`, muted tints via `color-mix()`, not full-saturation fills).
- **Dark mode**: `ThemeToggle.astro` (vanilla JS, no framework) toggles `data-theme` on `<html>` and persists to `localStorage`. `BaseHead.astro` has a render-blocking inline script that applies the stored preference before first paint (no flash). The toggle's click handler is bound via event delegation on `document`, not the button directly — View Transitions swaps/recreates the header on every client-side navigation, so a handler bound to the button itself would silently stop working after the first navigation.
- **Fonts**: two families only (deliberately not three — keeps it "restrained"). Atkinson Hyperlegible for body *and* headings (bold weight for headings, no separate display face). IBM Plex Mono reserved strictly for metadata: dates, tags, breadcrumbs, pillar labels, code blocks — anywhere the `.meta` utility class is used. Both are declared in `astro.config.mjs`'s `fonts` array *and* must be rendered via `<Font cssVariable="..." />` in `BaseHead.astro` — declaring a font in config without rendering it via `<Font>` silently does nothing (`var(--font-mono)` just falls back to generic `monospace`).
- **Shared components** (`src/components/`): `Button` (primary/secondary/ghost, renders `<a>` or `<button>`), `Card` (bordered list-item wrapper; exposes `--card-hover-color` custom property so slotted headings can react to card hover without needing `:global()` — Astro's CSS scoping means a parent's `<style>` can't target a child component's elements by tag name), `Badge` (neutral, or pillar-tinted via `variant="pillar"` — used for a paper's pillar *or*, with `variant="neutral"`, a format label like "Essay"/"Memo" on cards that mix formats), `Breadcrumbs`, `RecentResearch` (self-contained: fetches + renders the 3 most recent `research` entries across all formats, used on the homepage and the 404 page), `RelatedResearch` (up to 3 entries sharing the current one's pillar and/or tags — pillar scoring only applies between papers, since essays/memos have no pillar), `SocialLinks` (LinkedIn/Substack/GitHub icons, footer only — deliberately not in the header, which stays limited to primary nav + search + theme toggle; reads from `SOCIAL_LINKS` but only renders these three via its own local `links` array, so adding a new key to `SOCIAL_LINKS` — e.g. `orcid` — does not automatically add a footer icon), `ThemeToggle`, `TableOfContents` (sticky rail with scroll-spy, gated behind a heading-count threshold — see below), `ScrollProgress` (fixed bar at the top of the viewport, fills with scroll position on every research page — rendered once inside `ArticleShell.astro`, so `ResearchLayout` gets it automatically with no per-layout wiring; no heading-count gating, unlike the TOC, since it's cheap even on short pages).
- **Layout** (`src/layouts/`): one `ResearchLayout.astro` for every format (papers, essays, memos alike — merged from separate `PaperLayout.astro`/`BlogPost.astro` layouts 2026-08-20, see "Collections" below), built on the shared `ArticleShell.astro` (title/date/prose shell, named slots — `hero`, `before-title`, `after-title`, `mobile-toc`, `toc`, default). `ResearchLayout` emits JSON-LD that branches on `format`: `'@type': ['ScholarlyArticle', 'Article']` for papers, plain `'Article'` for essays/memos (schema.org has no distinct essay/memo type); `isPartOf`/`articleSection` (pillar linkage) only for papers. Otherwise shared: `headline`/`image`/dates, `wordCount`/`timeRequired` from the reading-time remark plugin, `inLanguage`, `author.sameAs` sourced from `SOCIAL_LINKS` in `src/consts.ts` (deliberately no `publisher` or `license`, not forgotten, just not decided), and a `BreadcrumbList`. `index.astro` (the homepage) emits its own separate `Person` + `WebSite` JSON-LD — the entity graph establishing Amul Bham as a disambiguated author, `Person.sameAs` sourced from the same `SOCIAL_LINKS`. This schema is inert until the site-wide noindex is lifted (see "Indexing state" above) — built ahead of launch deliberately, same as the OG image routes.
- **OG images**: `src/pages/open-graph/[...route].ts` covers the whole `research` collection, keyed by `${categorySegment(entry)}/${id}` (see "Categories/URLs" below) — pillar-tinted border for papers, plain `--accent` border for essays/memos (no pillar to derive a color from).
- **Table of contents**: only renders when an entry has **6 or more `##` headings** — this was measured against real papers, not guessed, and confirmed still correct when scroll-spy was added (kept at 6 rather than lowered, per an explicit decision — see `CHANGELOG.md` 2026-08-18). Only `##`-level headings are surfaced (not `###`). `TableOfContents.astro` takes a `variant` prop (`'rail' | 'mobile' | 'both'`, default `'both'`) — `ResearchLayout.astro` renders it twice, once per variant, into `ArticleShell.astro`'s separate `toc` (desktop sticky rail) and `mobile-toc` (a `<details>` disclosure, <1100px, auto-collapses on link tap) slots. Its init script (scroll-spy `IntersectionObserver` + mobile auto-collapse) lives in `ArticleShell.astro`, not the component itself — a script inside a twice-rendered component runs twice, and `ArticleShell` is the nearest ancestor guaranteed to render exactly once per page (a real bug found and fixed 2026-08-19, inherited from an other-platform session's work). Reinitializes on `astro:page-load`, not `DOMContentLoaded`, following the same View Transitions pattern as Pagefind's init in `search.astro`.

### Content-section transforms — standing policy

Recurring content-section patterns (References today; others as they actually recur — don't pre-build for sections that don't exist yet) get a **build-time remark/rehype transform**, registered in `astro.config.mjs`'s `markdown.processor: unified({ remarkPlugins, rehypePlugins })`. Not MDX, not hand-written components in content files. This is a deliberate policy, not just how it happened to get built: it means authoring stays plain Markdown — paste it exactly as before, the transform recognizes known section shapes and styles them automatically. Reserve MDX/real components for anything that genuinely can't be expressed as plain Markdown (real interactivity, data that doesn't fit a list/table shape) — nothing on this site needs that yet.

All registered together in `astro.config.mjs`'s `markdown.processor: unified({ remarkPlugins: [remarkReadingTime, remarkAlert], rehypePlugins: [rehypeReferences, rehypeTableWrap] })`. Three are hand-rolled, zero-dependency plain functions in `src/lib/`; one (`remarkAlert`) is a deliberate exception to that — see below.

- `remark-reading-time.mjs` — operates on the **mdast** (markdown AST, before HTML conversion), computes `wordCount`/`minutesRead` into `remarkPluginFrontmatter`.
- `rehype-section-utils.mjs` — shared factory, `createHeadingSectionWrapper({ headingText, sectionClass, listTags, onWrap })`, extracted from `rehype-references.mjs` once a second heading+list transform (`rehype-key-findings.mjs`) needed the identical detection logic. Operates on the **hast**. Restructuring/wrapping actual elements is a rehype job, not remark — mdast has no clean way to express an arbitrary wrapper element. **Gotcha already hit once**: the heading and list are *not* strictly adjacent siblings in the tree — there's a whitespace-only text node (a literal `"\n"`) between them from the blank line in the source Markdown, so this skips whitespace text nodes when looking for "the next real sibling," not assume `children[i + 1]` is it.
- `rehype-references.mjs` — `createHeadingSectionWrapper({ headingText: 'references', sectionClass: 'references', listTags: ['ol'] })`. Restricted to `<ol>` only (unlike Key Findings, which also accepts a bullet list) since the `onWrap` callback assigns each `<li>` a stable `id="ref-N"` (1-based document order) — this only makes sense for a numbered reference list.
- `rehype-key-findings.mjs` — `createHeadingSectionWrapper({ headingText: 'key findings', sectionClass: 'key-findings' })`. Wraps a "Key Findings" heading + list (ordered or unordered) in `<section class="key-findings">`, styled as a highlighted callout box in `global.css` (reusing the `.pillar-card` visual language already live on `/about`, not a new treatment). Entirely opt-in — a paper without that heading renders nothing extra.
- `rehype-table-wrap.mjs` — operates on the **hast**, wraps every `<table>` (walking the whole tree, not just top-level children — unlike `rehype-references`, tables can appear inside list items) in `<div class="table-container" tabindex="0">`, styled with `overflow-x: auto` in `global.css` so wide tables scroll horizontally on narrow viewports instead of breaking `--content-width-prose`.
- `rehype-figures.mjs` — operates on the **hast**, walking the whole tree. Promotes a `<p>` whose only meaningful child is an `<img>` (the shape standard `![alt](src)` Markdown always produces — confirmed against Astro's actual built-in markdown image optimization output, not assumed) into `<figure><img/><figcaption>{alt}</figcaption></figure>`. Skips the `<figcaption>` entirely when alt text is empty, so a captionless image doesn't get an empty caption box — there's no separate flag for "has a caption," it's purely alt-text-driven.
- `rehype-citation-links.mjs` — **must run after `rehype-references.mjs`** (reads the `id="ref-N"` values it assigns). Auto-links inline citations to their reference-list entry: `(Bennett, 1987)` → `<a href="#ref-1">`. Built 2026-08-19 once real content confirmed every inline citation actually maps to a reference — this was previously deferred as "real text-parsing work, do it later" (see `CHANGELOG.md`), and real content turned out to need **two** citation shapes, not the one originally anticipated:
  - **Parenthetical** — `(Name, Year)`, including semicolon-separated multi-source groups `(Name1, Y1; Name2, Y2)` (each sub-citation linked individually, `(`/`;`/`)` left as plain text), and `(Name, n.d.)`. Matched by extracting the name from inside the already-paren-bounded group, then looking it up — safe because the literal `(`/`)` naturally bound where the candidate name starts and ends.
  - **Narrative** — `Name (Year)`, e.g. `Macartney et al. (2024)`, `O'Brien v. Weinberger (1978)` (a distinct legal-citation sub-shape: `Case Name v. Other Name (Year)`, `year` read from inside that specific parenthetical, not the first 19xx/20xx digit anywhere in the reference — a court citation's reporter/page numbers could otherwise be misread as the year). **Bug found and fixed while building this**: matching this shape against a *generic* capitalized-phrase pattern (`[A-Z][A-Za-z... ]+\(Year\)`) is unsafe — its leftmost-match preference grabs whatever capitalized text starts the enclosing sentence (`"As documented in Macartney et al. (2024)"` matched as the whole "name", not just `"Macartney et al."`), since unlike the parenthetical shape there's no literal `(` bounding where the name starts. Fixed by matching against the *known* reference names directly (an escaped regex alternation of every name already in the lookup table, sorted longest-first) instead of a generic pattern.
  - **Second bug found and fixed**: Astro's markdown pipeline smartypants-converts straight quotes to curly ones (`'` → `’`) before this plugin sees the text. The parenthetical shape's Map-based lookup already normalized this correctly on both sides; the narrative shape's regex *pattern* (built from already-normalized straight-quote lookup keys) didn't account for curly quotes in the *searched* text, silently failing to match `O’Brien v. Weinberger`. Fixed by searching a straight-quote copy of the text (same length, so match indices stay valid) while still slicing the final linked substring from the original text, preserving the curly quote actually rendered.
  - Fails closed throughout — anything that doesn't resolve to exactly one reference stays plain text. Verified against every one of the financial-aid paper's real inline citations (45 links, individually cross-checked against the 35-entry reference list) before shipping, not spot-checked.
- `remark-github-blockquote-alert` (npm package, not hand-rolled) — parses GFM alert syntax (`> [!NOTE]`, `[!TIP]`, `[!WARNING]`, `[!CAUTION]`, `[!IMPORTANT]`) into `<div class="markdown-alert markdown-alert-{severity}">` blocks. The one deliberate exception to "hand-roll it" in this policy: parsing multi-paragraph blockquote alerts correctly (nesting, multiple body paragraphs) has more edge cases than the References/table wrappers, and this package already handles them, is actively maintained, and adds a single small transitive dependency (`unist-util-visit`). Its default GitHub-styled CSS is **not** imported — `global.css` re-themes the `.markdown-alert*` classes with this site's own tokens (`--alert-note/tip/important/warning/caution`, same muted-tint `color-mix()` treatment as `--pillar-*`) so it stays consistent in dark mode.

Section-transform CSS (`.references*`, `.table-container`, `.markdown-alert*`, `figure`/`figcaption`, `.key-findings*`) goes in `global.css`, unscoped — same reason `.prose p`/`code`/`pre`/`blockquote` are unscoped there: Astro's component-scoped `<style>` can't reach markup injected via `<slot />` from rendered Markdown, only markup written directly in that `.astro` file's own template.

## Content

- **One collection, three formats**: `src/content.config.ts` defines a single `research` collection, distinguished by a `format: 'paper' | 'essay' | 'memo'` field. Unified 2026-08-20 from what were previously two separate collections (`papers`, `blog`) with separate schemas/layouts/routes — the split turned out to cost more in duplicated maintenance (two layouts to update every time a shared feature landed, two index pages, two route trees) than it bought, and fragmented the reader-facing browsing experience across `/research-hub/` and `/blog/`. **`paper`**: rigorous, protocol-driven research, requires `pillar`, gets `ScholarlyArticle` JSON-LD. **`essay`**: long-form analytical prose, no pillar, plain `Article` JSON-LD. **`memo`**: shorter, more casual notes, same shape as essay — a category with room to grow into, no entries yet. Currently 1 paper (the FAFSA/financial-aid piece) and 1 essay (on frontier model training economics); the placeholder sample content used during the initial build was removed 2026-08-19 so nothing fake gets crawled.
- **Content lives in per-slug folders**: `src/content/research/<slug>/index.md`, not flat `<slug>.md` files (so each entry can have images alongside it). The content-layer `glob()` loader strips a trailing `/index` from the generated slug (confirmed directly from Astro's source, `content/utils.js`'s `getContentEntryIdAndSlug`), so `entry.id` is unaffected by the folder structure — still the bare slug. Any image referenced from an entry's body via a relative path (e.g. `./figure-1.png`) should live in that same folder.
- **Frontmatter** — required: `title`, `format`, `pubDate`, `description`, `excerpt`. `pillar` is required *only* when `format: 'paper'` (enforced via a schema `.refine()`, not just convention — a paper without a pillar fails the build). Optional: `tags` (defaults to `[]`), `dateModified`, `pdfUrl`, `heroImage`, `heroImageAlt`. An optional `## Key Findings` heading (followed by a list, ordered or unordered) anywhere in the body gets auto-styled as a highlighted callout box — see "Content-section transforms" above. **No `canonicalURL` field** — it's derived in `ResearchLayout.astro` (via `src/lib/research-routing.ts`, see below) from the category + slug, specifically so it can never drift from the actual route (this happened once: a paper's `canonicalURL` frontmatter still said its old pillar after the `pillar` field itself was updated, silently breaking that page's JSON-LD `url` for a while).
- **`description` vs `excerpt`**: `description` is the full abstract — used only for the JSON-LD `description` field (schema.org has no length concern there). `excerpt` (`z.string().max(200)`, aim for ~155–160 chars) is the short summary used for the actual `<meta name="description">`/OG description tag and every card blurb site-wide: `RecentResearch.astro`, `RelatedResearch.astro`, `research-hub/index.astro`, `research-hub/[category]/index.astro`, `tags/[tag]/index.astro`, and `rss.xml.js`. Always write both — the schema has no fallback if `excerpt` is missing. (Split out 2026-08-19 after a real bug: the FAFSA paper's full ~1600-character abstract was being used verbatim as the meta tag and every listing blurb.)
- **Categories/URLs** (`src/lib/research-routing.ts`) — single source of truth for how an entry maps to a URL, so this can't drift the way `canonicalURL` frontmatter once did: `categorySegment(entry)` returns a paper's `pillar` slug, or the pluralized `format` for anything else (`essays`, `memos`). `canonicalPath(entry)` builds the full `/research-hub/{category}/{slug}/` path from that. Used by the `[category]/[slug].astro` route, `ResearchLayout`'s `canonicalURL`, the OG image route, and both index pages. Papers keep the URL shape they've always had; essays/memos live at `/research-hub/essays/{slug}/` and `/research-hub/memos/{slug}/`.
  - **Gotcha hit building this**: `research-hub/[category]/index.astro` needs `/research-hub/essays/` and `/research-hub/memos/` to always build, even with zero entries (unlike pillars, which only get a page once they have a paper — `essays`/`memos` are fixed, permanent taxonomy categories, not ad-hoc pillar slugs). The fix (a `forcedCategories` array unioned into the categories `getStaticPaths` returns) **must be declared inside `getStaticPaths` itself**, not as a sibling top-level `const` in the same file — Astro extracts `getStaticPaths` into an isolated build-time chunk that doesn't reliably close over other module-scope consts declared alongside it in the same `.astro` file (a real build failure, `"FORCED_CATEGORIES is not defined"`, confirmed this the hard way). Values needed inside `getStaticPaths` must be either declared inside the function or imported from another module — not just declared as a sibling const.
- **Images — the spec to prepare per entry**:
  - **Hero image** (optional, top-of-page banner): `heroImage` + `heroImageAlt` (required together — a schema `.refine()` enforces this, since a real hero isn't decorative). **1020×510 (2:1)**, PNG or JPG. Auto-optimized to WebP with `width`/`height` set (no layout shift) via Astro's built-in Markdown/content-collection image pipeline — no manual resizing needed beyond providing one reasonably sized source.
  - **Inline figures** (optional, anywhere in the body): plain `![alt text](./relative-path.png)` Markdown — `rehype-figures.mjs` auto-promotes a solo image into a captioned `<figure>`. No fixed aspect ratio, but ≥1200px on the long edge recommended (the prose column is 720px; this gives retina-quality downscaling headroom). Alt text becomes the visible caption — provide it when the image needs one, omit it (`![](...)`) for a plain uncaptioned figure.
- **Pillars** (4, papers only): `ai-systems`, `seo-architecture`, `systems-architecture`, `policy-systems`. Each needs an entry in `PILLAR_DESCRIPTIONS` (`src/lib/pillars.ts`) for its landing page intro copy, and a `--pillar-*` color token in `global.css` if a 5th is ever added.
- **Tags**: free-text in frontmatter (e.g. `"Dependency Paradox"`), slugified for routing via `slugifyTag()` (`src/lib/tags.ts`) so casing/spacing variants land on the same `/tags/` page. `tags/[tag]/index.astro` queries the one `research` collection directly (papers get a pillar-tinted `Badge`, essays/memos get a neutral format-label badge). No enforced vocabulary — see `ROADMAP.md` for why that's deliberate for now.
- **Adding new research**: create `src/content/research/<slug>/index.md`, frontmatter per the schema above (remember `pillar` for papers, skip it for essays/memos). Reading time, the table of contents, the OG image, the RSS feed, the tag pages, the category index page, and related-research cross-links are all generated automatically at build time from that one file — nothing else to touch.
- **`/about`**: real researcher-profile content (not the starter's Lorem Ipsum placeholder as of 2026-08-19) — research pillars, methodology, and a verified-credentials list (ORCID/LinkedIn/Substack/GitHub/email) sourced from `SOCIAL_LINKS`. Emits its own `ProfilePage` + `Person` JSON-LD, separate from the homepage's `Person`/`WebSite` schema and each entry's `author` field.
