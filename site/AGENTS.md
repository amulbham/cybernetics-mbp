# cybernetics-mbp

Personal research hub for Amul Bham (amulbham.com) — Astro 7, static output, deployed on Cloudflare Pages. This file auto-loads every session. **At the start of new work, read `ROADMAP.md` for pending items and `CHANGELOG.md` for recent history** — both are real files in this repo, not auto-loaded, so they have to be opened deliberately. **For what a research page *is* — frontmatter, transforms, layout, grammar, presentation, all in one map — read `PUBLISHING.md`**, the publishing specification; this file (`AGENTS.md`) stays the pipeline/routing/deploy reference underneath it.

## Development

```sh
astro dev --background
```

Manage with `astro dev stop`, `astro dev status`, `astro dev logs`. Search (`/search`, Pagefind) and OG images only work against a built site — `astro dev` can't serve either. To test them: `npm run build && astro preview`.

**If you change the markdown pipeline (add/edit a remark or rehype plugin in `astro.config.mjs`) and the build doesn't reflect it**: clear `node_modules/.astro/` (its `data-store.json` is a content-layer cache, separate from `.astro/` and Vite's cache, and it can silently keep serving previously-rendered HTML even after `dist`/`.astro` are cleared). This cost real debugging time once already — `rm -rf node_modules/.astro dist .astro` before rebuilding if a markdown-pipeline change doesn't seem to be taking effect.

## Deploy workflow — staging → production

- **`main`** is production. Cloudflare Pages watches it and auto-deploys to `amulbham.com` on every push.
- **`staging`** is the working branch. Every push gets its own live Cloudflare Pages preview build, fully isolated from production. Stable branch alias: `https://staging.cybernetics-mbp-site.pages.dev/` (always reflects the latest push to `staging`; per-commit preview URLs like `https://<hash>.cybernetics-mbp-site.pages.dev/` also exist but change on every push).
- **Day-to-day**: do work on `staging`, push, check the preview, iterate as many times as needed — nothing reaches `amulbham.com` until `staging` is merged into `main`. Merge via GitHub PR (`github.com/amulbham/cybernetics-mbp/pull/new/staging`) or a direct `git merge staging` into `main` — either way, verify the live preview *before* merging and re-verify production *after*, since a merge triggering a build isn't the same as confirming the build actually shipped what you expect.
- Cloudflare Pages project settings: root directory `site` (the repo root isn't the Astro project), build command `npm run build` (this already includes the Pagefind indexing step — see below), output directory `dist`, Node 22+. **Transitional as of Sprint 8.2**: scholarly paper PDFs (`paper.pdf`, same directory as each paper's `index.html`) are built by `.github/workflows/deploy-pages.yml` in GitHub Actions, not by Cloudflare's own Node build — Cloudflare's build image is undocumented for headless-Chrome support and runs inside a gVisor sandbox (see `CHANGELOG.md`'s Sprint 8.0 entry), so PDF typesetting happens in Actions and the finished `dist/` (HTML + PDFs together) is handed to Cloudflare via `wrangler pages deploy`, never built by Cloudflare itself. This requires two steps neither of which is done automatically by this repo: `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID` as GitHub repository secrets, and — in the Cloudflare Pages dashboard — Build → Branch control → automatic deployments turned **off** for both the production branch and preview branches. Until both are done, Cloudflare's own Git integration is still live and still running its own `npm run build` on every push (HTML only, no PDFs) exactly as described above — check which is actually true before assuming PDFs are live on a given deploy.
- **When polling a preview/production URL to confirm a deploy landed, check for a marker that's only true on the *new* build — not just present on both old and new.** A `grep -q "some string"` check that's already true on the previous deploy will report "live" immediately without the new build having actually shipped (hit this for real: checking for `"function initToc"` passed instantly because the *old, buggy* build already contained that string too — just twice instead of once — so the fix's absence went unnoticed until the actual occurrence *count* was checked). Also add a cache-busting query param (`?cb=<random>`) when re-checking after a fix — Cloudflare's edge cache can keep serving stale HTML for a bit past when the new build actually finished.

## Indexing state — READ BEFORE TOUCHING

The site is **deliberately deindexed** while content/design work continues:

- `public/robots.txt` → `Disallow: /`
- `src/components/BaseHead.astro` → `const SITE_WIDE_NOINDEX = true;` forces `noindex, nofollow` on every page via the `<SEO/>` call, regardless of environment (staging and production both stay deindexed).
- Individual pages can still force `noindex` themselves via `<BaseHead noindex />` regardless of the site-wide flag (used by `404.astro`, since a 404 should never be indexed even after launch).

**Do not flip `SITE_WIDE_NOINDEX` to `false` or restore `robots.txt` to `Allow: /` without the user explicitly asking for it.** When they do: flip both together (they were designed as one change), and restore the `Sitemap: https://amulbham.com/sitemap-index.xml` line in `robots.txt` at the same time.

## Design system

**Visual contract: `site/design-system/`** (`README.md`, `tokens.md`, `components.md`, `do-not.md`). Do not invent color, type, or chrome that isn't in that folder. Content pipeline rules (frontmatter, citation conventions, routing, deploy discipline) stay in this file — that folder is visual only.

- **Tokens**: `src/styles/global.css`. Semantic color tokens (`--bg`, `--text-primary`, `--text-secondary`, `--accent`, `--border`, etc.) with a `:root[data-theme='dark']` override block plus a `@media (prefers-color-scheme: dark)` fallback for users who haven't made an explicit choice. Also: spacing (`--space-1`…`--space-8`), radius (`--radius-sm/md/lg/full`), a modular type scale (`--text-xs`…`--text-4xl`), two content-width tokens (`--content-width-prose` 720px for reading columns, `--content-width-wide` 960px for grids/listings), and per-pillar accent colors (`--pillar-*`, muted tints via `color-mix()`, not full-saturation fills) plus admonition-severity colors (`--alert-*`). **Every color token needs an explicit dark-mode value in both the `:root[data-theme='dark']` block and the `@media` fallback** — `--pillar-*`/`--alert-*` shipped without one for a while (a real bug, found 2026-08-20: `--pillar-ai-systems` was the exact same hex as light mode's `--accent`, which itself needed a brighter dark-mode value to stay legible; pillar/alert colors never got the same treatment, so badges and admonitions read muddy in dark mode while everything else looked fine). Check both blocks when adding a new color token, not just one.
- **Dark mode**: `ThemeToggle.astro` (vanilla JS, no framework) toggles `data-theme` on `<html>` and persists to `localStorage`. `BaseHead.astro` has a render-blocking inline script that applies the stored preference before first paint (no flash) — this same function **also runs on `astro:after-swap`**, not just once on initial load, since Astro's `<ClientRouter />` swaps `<head>`/`<body>` on every internal navigation to match the destination page's static HTML, which never has `data-theme` baked into it (only this script ever adds it). Without the `astro:after-swap` re-run, toggling dark mode then clicking any internal link silently reverted to light — a real bug, found and fixed 2026-08-20. The toggle's click handler is bound via event delegation on `document`, not the button directly — View Transitions swaps/recreates the header on every client-side navigation, so a handler bound to the button itself would silently stop working after the first navigation.
- **Fonts**: two families only (deliberately not three — keeps it "restrained"). Atkinson Hyperlegible for body *and* headings (bold weight for headings, no separate display face). IBM Plex Mono reserved strictly for metadata: dates, tags, breadcrumbs, pillar labels, code blocks — anywhere the `.meta` utility class is used. Both are declared in `astro.config.mjs`'s `fonts` array *and* must be rendered via `<Font cssVariable="..." />` in `BaseHead.astro` — declaring a font in config without rendering it via `<Font>` silently does nothing (`var(--font-mono)` just falls back to generic `monospace`).
- **Shared components** (`src/components/`): `Button` (primary/secondary/ghost, renders `<a>` or `<button>`), `Card` (bordered list-item wrapper; exposes `--card-hover-color` custom property so slotted headings can react to card hover without needing `:global()` — Astro's CSS scoping means a parent's `<style>` can't target a child component's elements by tag name), `Badge` (neutral, or pillar-tinted via `variant="pillar"` — used for a paper's pillar *or*, with `variant="neutral"`, a format label like "Essay"/"Memo" on cards that mix formats; the pillar variant also gets a subtle tinted border, `color-mix(... 20%, transparent)` of the same `--badge-color`, one step darker than the 12% tint used for the background), `Breadcrumbs`, `RecentResearch` (self-contained: fetches + renders the 3 most recent `research` entries across all formats, used on the homepage and the 404 page), `RelatedResearch` (up to 3 entries sharing the current one's pillar and/or tags — pillar scoring only applies between papers, since essays/memos have no pillar), `SocialLinks` (footer only — deliberately not in the header, which stays limited to primary nav + search + theme toggle; reads from `SOCIAL_LINKS` but only renders these three via its own local `links` array, so adding a new key to `SOCIAL_LINKS` — e.g. `orcid` — does not automatically add a footer chip. Renders as mono-font bordered text-abbreviation chips (`in`/`S`/`</>`), not icons — this site deliberately has no icon library, per the design system imported 2026-08-24), `ThemeToggle`, `TableOfContents` (sticky rail with scroll-spy, gated behind a heading-count threshold — see below; the active/hovered link also gets a left accent border, not just a color change), `ScrollProgress` (fixed bar at the top of the viewport, fills with scroll position on every research page — rendered once inside `ArticleShell.astro`, so `ResearchLayout` gets it automatically with no per-layout wiring; no heading-count gating, unlike the TOC, since it's cheap even on short pages).
- **Article masthead**: `ArticleMasthead.astro`, rendered by `ResearchLayout.astro` at the top of the `after-title` slot (same slot tags/pdf-link already occupy). Renders name/affiliation/correspondence/format/license entirely from `AUTHOR`/`LICENSE`/`SOCIAL_LINKS` in `consts.ts` plus the existing `formatLabel()` helper — **no frontmatter needed**, since this data is identical on every entry by a solo author. Added 2026-08-24 specifically because the equivalent content used to be hand-typed Markdown in each article's body, and two early pieces had already drifted into different formats from each other within days — see `CHANGELOG.md`. If a new piece ever has hand-typed byline content in its body, that's a bug to fix (delete it, let the component render it), not a style choice.
- **Header logo**: `Header.astro` renders the "AB" geometric ligature mark (v2, replacing the original design-system serif+dots monogram same-day 2026-08-24 — a flat two-tone shape scales to favicon sizes far better) as **two** assets, `logo-header-light.png`/`logo-header-dark.png` (`src/assets/`, imported via Astro's `<Image>`), toggled by CSS using the exact same `[data-theme='dark']`/`prefers-color-scheme` guard pattern as every color token in `global.css` and `ThemeToggle.astro`'s own sun/moon icon swap — not a single raster image, since the mark needs to flip color with the theme. `alt=""` on both — the adjacent site-title text already names the site, a redundant alt would just repeat it. Source assets trimmed from padded originals via a one-off `sharp` script (not kept in the repo).
- **Favicon light/dark pair**: `BaseHead.astro` links `favicon.svg`/`favicon-32x32.png` (light-mode, dark mark) and `favicon-dark.svg`/`favicon-32x32-dark.png` (dark-mode, light mark) via `media="(prefers-color-scheme: ...)"` — the standard technique, and the most a static `<link>` can do (it reacts to the OS preference, not this site's own manual toggle, since the browser evaluates favicon `media` independent of page JS/CSS). `favicon.ico` and `apple-touch-icon.png` stay single assets (dark mark) since neither legacy bookmark bars nor iOS home-screen icons support per-scheme swapping.
- **Layout** (`src/layouts/`): one `ResearchLayout.astro` for every format (papers, essays, memos alike — merged from separate `PaperLayout.astro`/`BlogPost.astro` layouts 2026-08-20, see "Collections" below), built on the shared `ArticleShell.astro` (title/date/prose shell, named slots — `hero`, `before-title`, `after-title`, `mobile-toc`, `toc`, default). `ResearchLayout` emits JSON-LD that branches on `format`: `'@type': ['ScholarlyArticle', 'Article']` for papers, plain `'Article'` for essays/memos (schema.org has no distinct essay/memo type); `isPartOf`/`articleSection` (pillar linkage) only for papers. Otherwise shared: `headline`/`image`/dates, `wordCount`/`timeRequired` from the reading-time remark plugin, `inLanguage`, `license` (sourced from `LICENSE.url` in `consts.ts` — CC BY-NC 4.0 sitewide, decided 2026-08-24 after finding the footer and one article's own text directly contradicted each other on this), `author.sameAs` sourced from `SOCIAL_LINKS` in `src/consts.ts` (deliberately still no `publisher`, not forgotten, just not decided), and a `BreadcrumbList`. `index.astro` (the homepage) emits its own separate `Person` + `WebSite` JSON-LD — the entity graph establishing Amul Bham as a disambiguated author, `Person.sameAs` sourced from the same `SOCIAL_LINKS`. This schema is inert until the site-wide noindex is lifted (see "Indexing state" above) — built ahead of launch deliberately, same as the OG image routes.
- **OG images**: `src/pages/open-graph/[...route].ts` covers the whole `research` collection, keyed by `${categorySegment(entry)}/${id}` (see "Categories/URLs" below) — pillar-tinted border for papers, plain `--accent` border for essays/memos (no pillar to derive a color from).
- **Table of contents**: only renders when an entry has **6 or more `##` headings** — this was measured against real papers, not guessed, and confirmed still correct when scroll-spy was added (kept at 6 rather than lowered, per an explicit decision — see `CHANGELOG.md` 2026-08-18). Only `##`-level headings are surfaced (not `###`). `TableOfContents.astro` takes a `variant` prop (`'rail' | 'mobile' | 'both'`, default `'both'`) — `ResearchLayout.astro` renders it twice, once per variant, into `ArticleShell.astro`'s separate `toc` (desktop sticky rail) and `mobile-toc` (a `<details>` disclosure, <1100px, auto-collapses on link tap) slots. Its init script (scroll-spy `IntersectionObserver` + mobile auto-collapse) lives in `ArticleShell.astro`, not the component itself — a script inside a twice-rendered component runs twice, and `ArticleShell` is the nearest ancestor guaranteed to render exactly once per page (a real bug found and fixed 2026-08-19, inherited from an other-platform session's work). Reinitializes on `astro:page-load`, not `DOMContentLoaded`, following the same View Transitions pattern as Pagefind's init in `search.astro`.

### Content-section transforms — standing policy

Recurring content-section patterns (References today; others as they actually recur — don't pre-build for sections that don't exist yet) get a **build-time remark/rehype transform**, registered in `astro.config.mjs`'s `markdown.processor: unified({ remarkPlugins, rehypePlugins })`. Not MDX, not hand-written components in content files. This is a deliberate policy, not just how it happened to get built: it means authoring stays plain Markdown — paste it exactly as before, the transform recognizes known section shapes and styles them automatically. Reserve MDX/real components for anything that genuinely can't be expressed as plain Markdown (real interactivity, data that doesn't fit a list/table shape) — nothing on this site needs that yet.

**The full contract for every module — trigger, produces, authoring example, constraints, files — lives in `CONTENT-MODULES.md`, not here; don't paste individual contracts into this file.** That includes `rehype-research-primitive.mjs` (added Sprint 2, 2026-08-26): five shape-triggered `<aside>` kinds — definition, key-idea, evidence, counterpoint, implication — from a bolded blockquote label. Visual chrome (tokens, component styling) → `design-system/`. Content modules (what Markdown shape triggers what structure) → `CONTENT-MODULES.md`. The list below is kept only for the parts of the picture `CONTENT-MODULES.md` doesn't own (registration gotchas, npm-package exceptions, unscoped-CSS rationale) — when the two disagree on a fact, `CONTENT-MODULES.md` is authoritative for the module's contract.

All registered together in `astro.config.mjs`'s `markdown.processor: unified({ remarkPlugins: [remarkReadingTime, remarkAlert], rehypePlugins: [rehypeReferences, rehypeTableWrap, rehypeFigures, rehypeKeyFindings, rehypePullQuote, rehypeResearchPrimitive, rehypeCitationLinks, rehypeHeadingIds, rehypeResearchLinks] })`. All are hand-rolled, zero-dependency plain functions in `src/lib/`; `remarkAlert` is a deliberate exception to that — see below.

**Standing pipeline invariants for `rehype-research-links.mjs` (Sprint 7.5, 2026-09-01 — frozen 7.8)**:

- **Order is load-bearing: `rehypeCitationLinks` → `rehypeHeadingIds` → `rehypeResearchLinks`.** `rehypeHeadingIds` (imported from `@astrojs/markdown-remark`) has to be listed explicitly, positioned right before `rehypeResearchLinks`. Astro's own default heading-id assignment isn't part of this project's `rehypePlugins` array at all by default — the `unified()` config wrapper this project uses appends it unconditionally *after every plugin in that array*, once, at the very end of the real pipeline (confirmed from `@astrojs/markdown-remark`'s own `createMarkdownProcessor`). That's fine for every other plugin here, none of which read heading ids — but `rehypeResearchLinks` needs `id="..."` to already exist to resolve a relation's `inline.near`. Including `rehypeHeadingIds` here runs it a second, harmless time (it only assigns an id when one isn't already set); Astro's own automatic pass still runs again afterward regardless.
- **Never call `getEntry`/`astro:content` from inside a rehype plugin.** Confirmed by a real build failure, not assumed: `astro:content` is a Vite virtual module, unreachable from the plain-Node context a markdown rehype plugin runs in (`Only URLs with a scheme in: file, data, and node are supported`). A relation's target path is always resolved as `canonicalPath()` (from `research-routing.ts`) called on an object built from the target's own frontmatter (read directly via `parseFrontmatter`) — never a hand-built `/research/{pillar}/{id}/` string, and never an `astro:content` import from this layer.
- **A plugin throw alone is not the fail-closed gate — `scripts/validate-research-links.mjs` is.** Also confirmed directly: Astro's own content-layer glob loader catches a per-entry markdown render error, logs it, and *continues* — `astro build` exits 0 regardless, with the affected page silently missing content. `scripts/validate-research-links.mjs` runs the identical pipeline standalone, with no surrounding try/catch, and is the first step of `npm run build` (`tsx scripts/validate-research-links.mjs && astro build && pagefind --site dist`) specifically so the same failure is a real non-zero exit. Do not remove it from that script, and do not treat the plugin's own `throw` as sufficient on its own.

**Two validators, two different pipelines, do not conflate them (Sprint 8.6).** `scripts/validate-research-links.mjs` is a markdown-content gate — it runs *inside* `npm run build`, before `astro build`, on every push including Cloudflare's own native build. `scripts/validate-research-pdfs.mjs` (`npm run validate:pdfs`) is a Scholar/PDF-identity gate — it only makes sense **after** `npm run build:pdfs` has actually produced PDFs to check, so it runs as its own step in `.github/workflows/deploy-pages.yml`, between `build:pdfs` and `wrangler pages deploy`, and is deliberately **not** added to `npm run build` itself (Cloudflare's native build never produces PDFs — see "Transitional as of Sprint 8.2" above — so there'd be nothing for it to check there, and it would just fail every push). It discovers papers via the shared `scripts/discover-research.mjs` (also used by `build-research-pdfs.mjs`, so there is exactly one paper-discovery implementation, not two that can drift), parses each `paper.pdf` with `pdfjs-dist` (pinned exact version, never a raw-bytes/compressed-stream grep — see `CHANGELOG.md`'s Sprint 8.6 entry for why a real parse is load-bearing), and checks identity/link-structure only — it does not re-check the visual rows (table rendering, page-1 layout, primitive rendering) Sprint 8.5 already established stay a human raster check.

- `remark-reading-time.mjs` — operates on the **mdast** (markdown AST, before HTML conversion), computes `wordCount`/`minutesRead` into `remarkPluginFrontmatter`.
- `rehype-section-utils.mjs` — shared factory, `createHeadingSectionWrapper({ headingText, sectionClass, listTags, onWrap })`, extracted from `rehype-references.mjs` once a second heading+list transform (`rehype-key-findings.mjs`) needed the identical detection logic. Operates on the **hast**. Restructuring/wrapping actual elements is a rehype job, not remark — mdast has no clean way to express an arbitrary wrapper element. **Gotcha already hit once**: the heading and list are *not* strictly adjacent siblings in the tree — there's a whitespace-only text node (a literal `"\n"`) between them from the blank line in the source Markdown, so this skips whitespace text nodes when looking for "the next real sibling," not assume `children[i + 1]` is it.
- `rehype-references.mjs` — `createHeadingSectionWrapper({ headingText: 'references', sectionClass: 'references', listTags: ['ol'] })`. Restricted to `<ol>` only (unlike Key Findings, which also accepts a bullet list) since the `onWrap` callback assigns each `<li>` a stable `id="ref-N"` (1-based document order) — this only makes sense for a numbered reference list.
- `rehype-key-findings.mjs` — `createHeadingSectionWrapper({ headingText: 'key findings', sectionClass: 'key-findings' })`. Wraps a "Key Findings" heading + list (ordered or unordered) in `<section class="key-findings">`, styled as a highlighted callout box in `global.css` (reusing the `.pillar-card` visual language already live on `/about`, not a new treatment). Entirely opt-in — a paper without that heading renders nothing extra.
- `rehype-table-wrap.mjs` — operates on the **hast**, wraps every `<table>` (walking the whole tree, not just top-level children — unlike `rehype-references`, tables can appear inside list items) in `<div class="table-container" tabindex="0">`, styled with `overflow-x: auto` in `global.css` so wide tables scroll horizontally on narrow viewports instead of breaking `--content-width-prose`.
- `rehype-figures.mjs` — operates on the **hast**, walking the whole tree. Promotes a `<p>` whose only meaningful child is an `<img>` (the shape standard `![alt](src)` Markdown always produces — confirmed against Astro's actual built-in markdown image optimization output, not assumed) into `<figure><img/><figcaption>{alt}</figcaption></figure>`. Skips the `<figcaption>` entirely when alt text is empty, so a captionless image doesn't get an empty caption box — there's no separate flag for "has a caption," it's purely alt-text-driven.
- `rehype-pull-quote.mjs` — operates on the **hast**, walking the whole tree. Promotes a `<blockquote>` whose entire content is a single bolded line (`> **Not a score. A dependency.**`) into a large-type, centered "pull quote" (`class="pull-quote"`) for visual rhythm in long-form text — a restated key line, duplicated from the body, not a new sentence. Doesn't collide with GFM alerts: those are consumed by `remarkAlert` during the **remark** phase, so by the time this rehype plugin runs they're already `<div class="markdown-alert...">` elements, not blockquotes at all. Ordinary citation blockquotes are unaffected too — their content isn't a single whole-line `<strong>`, so the shape check excludes them. Added 2026-08-20 for the frontier-model essay, which read as too text-dense without any visual breaks.
- `rehype-citation-links.mjs` — **must run after `rehype-references.mjs`** (reads the `id="ref-N"` values it assigns). Auto-links inline citations to their reference-list entry: `(Bennett, 1987)` → `<a href="#ref-1">`. Built 2026-08-19 once real content confirmed every inline citation actually maps to a reference — this was previously deferred as "real text-parsing work, do it later" (see `CHANGELOG.md`), and real content turned out to need **two** citation shapes, not the one originally anticipated:
  - **Parenthetical** — `(Name, Year)`, including semicolon-separated multi-source groups `(Name1, Y1; Name2, Y2)` (each sub-citation linked individually, `(`/`;`/`)` left as plain text), and `(Name, n.d.)`. Matched by extracting the name from inside the already-paren-bounded group, then looking it up — safe because the literal `(`/`)` naturally bound where the candidate name starts and ends.
  - **Narrative** — `Name (Year)`, e.g. `Macartney et al. (2024)`, `O'Brien v. Weinberger (1978)` (a distinct legal-citation sub-shape: `Case Name v. Other Name (Year)`, `year` read from inside that specific parenthetical, not the first 19xx/20xx digit anywhere in the reference — a court citation's reporter/page numbers could otherwise be misread as the year). **Bug found and fixed while building this**: matching this shape against a *generic* capitalized-phrase pattern (`[A-Z][A-Za-z... ]+\(Year\)`) is unsafe — its leftmost-match preference grabs whatever capitalized text starts the enclosing sentence (`"As documented in Macartney et al. (2024)"` matched as the whole "name", not just `"Macartney et al."`), since unlike the parenthetical shape there's no literal `(` bounding where the name starts. Fixed by matching against the *known* reference names directly (an escaped regex alternation of every name already in the lookup table, sorted longest-first) instead of a generic pattern.
  - **Second bug found and fixed**: Astro's markdown pipeline smartypants-converts straight quotes to curly ones (`'` → `’`) before this plugin sees the text. The parenthetical shape's Map-based lookup already normalized this correctly on both sides; the narrative shape's regex *pattern* (built from already-normalized straight-quote lookup keys) didn't account for curly quotes in the *searched* text, silently failing to match `O’Brien v. Weinberger`. Fixed by searching a straight-quote copy of the text (same length, so match indices stay valid) while still slicing the final linked substring from the original text, preserving the curly quote actually rendered.
  - Fails closed throughout — anything that doesn't resolve to exactly one reference stays plain text. Verified against every one of the financial-aid paper's real inline citations (45 links, individually cross-checked against the 35-entry reference list) before shipping, not spot-checked.
  - **Third round of bugs found and fixed 2026-08-24**, stress-testing against a real 32-reference cross-disciplinary paper with citations back to 1850: (1) `extractReferenceKey` only ever registered a reference's *first* author as its lookup key, so a two-author entry ("Nicolis, G. & Prigogine, I.") couldn't match either its parenthetical `&` form or its narrative `and` form (real APA style uses `&` in parentheses, `and` in prose — both need to resolve) — fixed by also registering `"surname1 & surname2"` and `"surname1 and surname2"` as keys whenever a reference entry has exactly two authors. (2) The surname-detection regex used `[a-zA-Z]`, so a two-word surname ("Conway Morris", "Maynard Smith") or an accented one ("Poincaré", "Szathmáry") silently failed to match at all — fixed with a Unicode-aware `\p{L}` character class (`/u` flag) instead of an ASCII range. (3) The year regex was hardcoded to `(19|20)\d{2}`, meaning *any* pre-1900 citation was structurally unmatchable — not a deliberate bound, just never tested against content old enough to hit it — widened to `(1[6-9]|20)\d{2}`. All three were real, generalizable gaps, not this-paper-only fixes. **What still fails closed by design, not a bug**: citing the same author's multiple works together in one group, comma- or semicolon-separated (`Kauffman (1969; 1993)`, `Clausius (1850, 1865)`) — only the first year links, since the trailing year has no name directly attached and the system correctly declines to guess rather than risk linking it to the wrong entry.
- `remark-github-blockquote-alert` (npm package, not hand-rolled) — parses GFM alert syntax (`> [!NOTE]`, `[!TIP]`, `[!WARNING]`, `[!CAUTION]`, `[!IMPORTANT]`) into `<div class="markdown-alert markdown-alert-{severity}">` blocks. The one deliberate exception to "hand-roll it" in this policy: parsing multi-paragraph blockquote alerts correctly (nesting, multiple body paragraphs) has more edge cases than the References/table wrappers, and this package already handles them, is actively maintained, and adds a single small transitive dependency (`unist-util-visit`). Its default GitHub-styled CSS is **not** imported — `global.css` re-themes the `.markdown-alert*` classes with this site's own tokens (`--alert-note/tip/important/warning/caution`, same muted-tint `color-mix()` treatment as `--pillar-*`) so it stays consistent in dark mode.

Section-transform CSS (`.references*`, `.table-container`, `.markdown-alert*`, `figure`/`figcaption`, `.key-findings*`) goes in `global.css`, unscoped — same reason `.prose p`/`code`/`pre`/`blockquote` are unscoped there: Astro's component-scoped `<style>` can't reach markup injected via `<slot />` from rendered Markdown, only markup written directly in that `.astro` file's own template.

## Content

- **One collection, three formats**: `src/content.config.ts` defines a single `research` collection, distinguished by a `format: 'paper' | 'essay' | 'memo'` field. Unified 2026-08-20 from what were previously two separate collections (`papers`, `blog`) with separate schemas/layouts/routes — the split turned out to cost more in duplicated maintenance (two layouts to update every time a shared feature landed, two index pages, two route trees) than it bought, and fragmented the reader-facing browsing experience across `/research-hub/` and `/blog/`. **`paper`**: rigorous, protocol-driven research, requires `pillar`, gets `ScholarlyArticle` JSON-LD. **`essay`**: long-form analytical prose, no pillar, plain `Article` JSON-LD. **`memo`**: shorter, more casual notes, same shape as essay — a category with room to grow into, no entries yet. Currently 2 papers (the FAFSA/financial-aid piece; a cross-disciplinary complexity-science paper, "The Invariants of Self-Organizing Systems," added 2026-08-24 as the real test case for the content-manager skill — see `.claude/skills/content-manager/`) and 1 essay (on frontier model training economics); the placeholder sample content used during the initial build was removed 2026-08-19 so nothing fake gets crawled.
- **Content lives in per-slug folders**: `src/content/research/<slug>/index.md`, not flat `<slug>.md` files (so each entry can have images alongside it). The content-layer `glob()` loader strips a trailing `/index` from the generated slug (confirmed directly from Astro's source, `content/utils.js`'s `getContentEntryIdAndSlug`), so `entry.id` is unaffected by the folder structure — still the bare slug. Any image referenced from an entry's body via a relative path (e.g. `./figure-1.png`) should live in that same folder.
- **Frontmatter** — required: `title`, `format`, `pubDate`, `description`, `excerpt`. Optional `subtitle`, rendered directly under the `<h1>` by `ArticleShell.astro` — use this instead of a `##` heading in the body for a subtitle: a heading gets picked up by the TOC transform as a real section (a real bug, found and fixed 2026-08-24 — the financial-aid paper's subtitle was showing up in its own TOC, right next to "Abstract"). `pillar` is required *only* when `format: 'paper'` (enforced via a schema `.refine()`, not just convention — a paper without a pillar fails the build). Optional: `tags` (defaults to `[]`), `dateModified`, `doi` (rendered in the masthead alongside the correspondence details when present), `heroImage`, `heroImageAlt`. **No `pdfUrl` field** — a paper's PDF has exactly one identity, `{canonicalURL}/paper.pdf`, derived in `ResearchLayout.astro` and shared by `citation_pdf_url`, the JSON-LD `MediaObject`, and the reader-facing Download PDF link (Sprint 8.4; see `PUBLISHING.md` §5) — the same discipline `canonicalURL` itself already used, for the same reason (a hand-authored field can drift from the real route; a derived one can't). An optional `## Key Findings` heading (followed by a list, ordered or unordered) anywhere in the body gets auto-styled as a highlighted callout box — see "Content-section transforms" above. **No `canonicalURL` field** — it's derived in `ResearchLayout.astro` (via `src/lib/research-routing.ts`, see below) from the category + slug, specifically so it can never drift from the actual route (this happened once: a paper's `canonicalURL` frontmatter still said its old pillar after the `pillar` field itself was updated, silently breaking that page's JSON-LD `url` for a while).
- **`description` vs `excerpt`**: `description` is the full abstract — used only for the JSON-LD `description` field (schema.org has no length concern there). `excerpt` (`z.string().max(200)`, aim for ~155–160 chars) is the short summary used for the actual `<meta name="description">`/OG description tag and every card blurb site-wide: `RecentResearch.astro`, `RelatedResearch.astro`, `research/index.astro`, `research/[category]/index.astro`, `tags/[tag]/index.astro`, and `rss.xml.js`. Always write both — the schema has no fallback if `excerpt` is missing. (Split out 2026-08-19 after a real bug: the FAFSA paper's full ~1600-character abstract was being used verbatim as the meta tag and every listing blurb.)
- **Categories/URLs** (`src/lib/research-routing.ts`) — single source of truth for how an entry maps to a URL, so this can't drift the way `canonicalURL` frontmatter once did: `categorySegment(entry)` returns a paper's `pillar` slug, or the pluralized `format` for anything else (`essays`, `memos`). `canonicalPath(entry)` builds the full `/research/{category}/{slug}/` path from that (renamed from `/research-hub/` 2026-08-24 to match the design system's route naming — free to do since nothing was indexed yet). Used by the `[category]/[slug].astro` route, `ResearchLayout`'s `canonicalURL`, the OG image route, and both index pages. Papers keep the URL shape they've always had; essays/memos live at `/research/essays/{slug}/` and `/research/memos/{slug}/`.
  - **Gotcha hit building this**: `research/[category]/index.astro` needs `/research/essays/` and `/research/memos/` to always build, even with zero entries (unlike pillars, which only get a page once they have a paper — `essays`/`memos` are fixed, permanent taxonomy categories, not ad-hoc pillar slugs). The fix (a `forcedCategories` array unioned into the categories `getStaticPaths` returns) **must be declared inside `getStaticPaths` itself**, not as a sibling top-level `const` in the same file — Astro extracts `getStaticPaths` into an isolated build-time chunk that doesn't reliably close over other module-scope consts declared alongside it in the same `.astro` file (a real build failure, `"FORCED_CATEGORIES is not defined"`, confirmed this the hard way). Values needed inside `getStaticPaths` must be either declared inside the function or imported from another module — not just declared as a sibling const.
- **Images — the spec to prepare per entry**:
  - **Hero image** (optional, top-of-page banner): `heroImage` + `heroImageAlt` (required together — a schema `.refine()` enforces this, since a real hero isn't decorative). **1020×510 (2:1)**, PNG or JPG. Auto-optimized to WebP with `width`/`height` set (no layout shift) via Astro's built-in Markdown/content-collection image pipeline — no manual resizing needed beyond providing one reasonably sized source.
  - **Inline figures** (optional, anywhere in the body): plain `![alt text](./relative-path.png)` Markdown — `rehype-figures.mjs` auto-promotes a solo image into a captioned `<figure>`. No fixed aspect ratio, but ≥1200px on the long edge recommended (the prose column is 720px; this gives retina-quality downscaling headroom). Alt text becomes the visible caption — provide it when the image needs one, omit it (`![](...)`) for a plain uncaptioned figure.
- **Pillars** (5, papers only): `ai-systems`, `seo-architecture`, `systems-architecture`, `policy-systems`, `cybernetics` (added 2026-08-24 for a cross-disciplinary complexity-science paper the original 4 didn't cover — don't force a paper into the closest approximate pillar; add a new one instead, it's cheap: a color token + a description, see below). Each needs an entry in `PILLAR_DESCRIPTIONS` (`src/lib/pillars.ts`) for its landing page intro copy, and a `--pillar-*` color token in `global.css` in all three locations (`:root`, the dark-mode override, and the `prefers-color-scheme` fallback) whenever a new one is added. The homepage's "Research pillars" grid (`index.astro`) reads `PILLAR_DESCRIPTIONS` directly and shows all pillars unconditionally regardless of paper count — it's category navigation, not a content listing, so a pillar with zero papers is still a legitimate place to browse to (unlike `research/index.astro`'s category sections, or `research/[category]/index.astro`, which only render/list once a pillar has content).
- **Tags**: free-text in frontmatter, slugified for routing via `slugifyTag()` (`src/lib/tags.ts`) so casing/spacing variants land on the same `/tags/` page. `tags/[tag]/index.astro` queries the one `research` collection directly (papers get a pillar-tinted `Badge`, essays/memos get a neutral format-label badge). No enforced vocabulary (see `ROADMAP.md`), but a **casing rule** decided 2026-08-24: sentence case by default (`financial aid`, `frontier models`), except a piece's own coined/named terms, which stay Title Case since they function as proper nouns (`Dependency Paradox`, `Bennett Hypothesis`).
- **Citation/external-linking convention by format**: papers use `(Author, Year)`/`Name (Year)` narrative citations, which `rehype-citation-links.mjs` auto-links to `#ref-N` (see "Content-section transforms" above). Essays/memos with freeform narrative citations (no safe structural marker to pattern-match) instead get a one-time manual editorial pass: hyperlink the actual phrase at first mention of each source directly to that source's URL — not a new auto-detection system, and not a rewrite of the piece's voice into parenthetical-citation style. Either way, every entry in the `## References` list must be a real external hyperlink, not plain text — that's the thing both citation styles depend on.
- **Adding new research**: create `src/content/research/<slug>/index.md`, frontmatter per the schema above (remember `pillar` for papers, skip it for essays/memos). Reading time, the table of contents, the OG image, the RSS feed, the tag pages, the category index page, and related-research cross-links are all generated automatically at build time from that one file — nothing else to touch.
- **`/about`**: real researcher-profile content (not the starter's Lorem Ipsum placeholder as of 2026-08-19) — research pillars, methodology, and a verified-credentials list (ORCID/LinkedIn/Substack/GitHub/email) sourced from `SOCIAL_LINKS`. Emits its own `ProfilePage` + `Person` JSON-LD, separate from the homepage's `Person`/`WebSite` schema and each entry's `author` field.
